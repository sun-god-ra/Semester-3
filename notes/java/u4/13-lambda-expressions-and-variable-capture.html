Lambda Expressions and Variable Capture

Object Oriented Programming Through Java · Unit IV: Multithreading and Lambda Expressions

Lambda Expressions and Variable Capture
Subject
Object Oriented Programming Through Java (24CS202)
Unit
Unit IV: Multithreading and Lambda Expressions
Topic
13 of 14

Practice: Part B questions for Unit IV and Part A short questions.

Notebook notes
  • A lambda can use local variables of the enclosing scope (capture) — but they must be effectively final (never modified after initialisation, not even by the lambda)
  • It can use and modify instance and static variables (they live on heap / class), and can use this (refers to the enclosing object, not the lambda)
  • A lambda parameter or local can't shadow a local variable of the enclosing method (compile error)
  • Reason: captured locals are copied into the lambda; a changing value would be inconsistent (and threads)
java
interface MyFunc { int func(int n); }

public class Capture {
    static int sfield = 0;
    public static void main(String[] args) {
        int num = 10;                         // effectively final
        MyFunc add = n -> { sfield++; return n + num; };
        System.out.println(add.func(8) + " " + sfield);
        // num++;   // would be a compile error: num is no longer effectively final
        int[] counter = {0};                  // workaround: mutable container
        Runnable r = () -> counter[0]++;
        r.run(); r.run();
        System.out.println(counter[0]);
    }
}
  • Output: 18 1, 2
Explanation

A lambda can use variables from the method in which it is written, but those local variables must be effectively final: they must not be changed after being given a value, whether in the lambda or outside it. The reason is that the lambda may run later, perhaps on a different thread, and it works on a copy of the value. If the original could change, the two would differ. Instance and static variables are not subject to this rule because they live in objects and classes that the lambda can reach directly. A common workaround to keep a changing counter is to use a one-element array or an AtomicInteger.
