Synchronization

Object Oriented Programming Through Java · Unit IV: Multithreading and Lambda Expressions

Synchronization
Subject
Object Oriented Programming Through Java (24CS202)
Unit
Unit IV: Multithreading and Lambda Expressions
Topic
7 of 14
Terms
Race condition, Synchronization, Mutual exclusion, Critical section, Deadlock

Practice: Part B questions for Unit IV and Part A short questions.

Notebook notes
  • Problem: when two threads use a shared resource at the same time → race condition, inconsistent data (e.g. two threads doing count++ — not atomic: read, add, write)
  • Synchronization = allow only one thread at a time to access the shared resource
  • Monitor (intrinsic lock): every Java object has a monitor. A thread that enters a synchronized method/block must acquire the object's lock; others block until it is released (mutual exclusion). Entering = lock, leaving (even by exception) = unlock
  • Synchronized method:
java
synchronized void call(String msg) { ... }
  • Synchronized block (finer grain; sync only the critical section; any object as lock):
java
synchronized (obj) {
    // statements that use obj
}
  • static synchronized method locks the Class object
  • Re-entrant: thread holding a lock can re-acquire the same lock
java
class Counter {
    private int c = 0;
    synchronized void inc() { c++; }
    int get() { return c; }
}

public class SyncDemo {
    public static void main(String[] args) throws InterruptedException {
        Counter ctr = new Counter();
        Runnable task = () -> { for (int i = 0; i < 10000; i++) ctr.inc(); };
        Thread t1 = new Thread(task), t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join(); t2.join();
        System.out.println("count = " + ctr.get());
    }
}
  • Output: count = 20000 (without synchronized, usually less than 20000)
  • Interthread communication: wait() (release the lock and sleep until notified), notify() (wake one waiting thread), notifyAll() (wake all). Must be called inside a synchronized context (else IllegalMonitorStateException). Classic: producer–consumer
  • Deadlock: thread A holds lock 1 and waits for lock 2, thread B holds lock 2 and waits for lock 1 → both wait forever. Prevent: consistent lock ordering, timeouts (tryLock), avoid nested locks
  • volatile — variable always read from main memory (visibility), not atomic. java.util.concurrent — ExecutorService, ReentrantLock, AtomicInteger (higher level)
  • Four Coffman conditions: mutual exclusion, hold and wait, no preemption, circular wait (see OS)
Explanation

Threads share objects, and that is dangerous when they change the same data. The statement c++ looks like one step, but it is three: read the value, add one, write it back. If two threads interleave those steps, one update is lost, which is a race condition. To prevent it, Java gives each object a lock, also called a monitor. A thread entering a synchronized method must first get the lock of that object. While it holds the lock no other thread can enter any synchronized method of the same object, so the steps are done one thread at a time. When the method finishes, even by an exception, the lock is released.

A synchronized block works the same way but protects only the few lines that need it, using the lock of an object you name, so other threads are blocked for a shorter time. In the demonstration, two threads each increment a shared counter 10000 times. With synchronization the result is always 20000. Without it, the result is usually less because increments get lost.

The methods wait, notify and notifyAll let threads cooperate. A thread that cannot continue calls wait(), which releases the lock and puts the thread to sleep. Another thread changes the condition and calls notify() to wake it up. They must be called from inside synchronized code. A deadlock occurs when threads each hold a lock needed by another and wait forever. A good prevention is to always acquire locks in the same order.
