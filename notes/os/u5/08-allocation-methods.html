Allocation Methods

Operating Systems · Unit V: Storage Management and File System

Allocation Methods

Operating Systems (24CS204)

Topic
8 of 10
Terms
External fragmentation, Internal fragmentation, Linked list, Inode, UNIX

Practice: Part B questions for Unit V and Part A short questions.

On this page
  1. Contiguous allocation
  2. Linked allocation
  3. Indexed allocation
Notebook notes
  • An allocation method refers to how disk blocks are allocated for files. Aim: utilise disk space effectively and allow fast access to files. Three major methods: contiguous, linked, indexed
Contiguous allocation
  • Each file occupies a set of contiguous blocks on the disk. Directory entry has the starting block (address) and the length (number of blocks): file of n blocks starting at b occupies b, b+1, …, b+n−1. Advantages: simple (only the starting location and the length needed); supports both sequential and direct access — block i of a file that starts at b is at b + i (fast, minimal seek time: fewer seeks, head movement minimised). Disadvantages: finding space for a new file — first fit / best fit (dynamic storage-allocation problem) → external fragmentation (compaction is expensive: off-line (unmount) or on-line); determining how much space is needed for a file (file growth: find a larger hole and copy — slow; or overestimate → internal fragmentation; extent-based variant: contiguous chunk (extent) with additional contiguous chunk added when it runs out — file = one or more extents; the location of a file's blocks = address, block count, plus a link to the first block of the next extent; used in Veritas File System, ext4). Modified contiguous allocation scheme: when the allocated space is not large enough, another chunk (extent) is added
Linked allocation
  • Each file is a linked list of disk blocks (blocks may be scattered anywhere on the disk); each block contains a pointer to the next block; directory contains a pointer to the first and last blocks of the file; to create a new file simply create a new entry in the directory with the pointer set to null; write → find a free block and link it at the end; read → follow pointers. Advantages: no external fragmentation; no need to declare file size in advance; file can continue to grow as long as free blocks exist; no compaction. Disadvantages: can be used effectively only for sequential-access files (to find the ith block you must follow i pointers → many disk reads, each a seek); space required for the pointers (e.g., a 512-byte block with 4-byte pointer → 0.78 % of the disk wasted; fix: group blocks into clusters → internal fragmentation, but fewer pointers and improved throughput); reliability — loss or damage of a pointer (a bug or hardware failure → the wrong block picked; partial fix: doubly linked list or store the file name and relative block number in each block → even more overhead). Effective data per block = block size − pointer size (e.g. 512 − 4 = 508 bytes)
  • File-allocation table (FAT): an important variation — a section of the disk at the beginning of each volume contains the table: one entry for each disk block, indexed by block number; the directory entry contains the block number of the first block of the file; the table entry indexed by that block number contains the block number of the next block; the last block has a special end-of-file value as its table entry; unused blocks are indicated by a 0 table value; allocating a new block = find the first 0-valued table entry and replace the previous end-of-file value with the address of the new block. Used by MS-DOS and OS/2; FAT12, FAT16, FAT32. Disadvantage: may result in significant number of disk head seeks unless the FAT is cached; benefit: random access time is improved (the disk head can find the location of any block by reading the information in the FAT)
    • Example: file test starting at block 217 → FAT[217] = 618, FAT[618] = 339, FAT[339] = EOF; so blocks: 217 → 618 → 339
Indexed allocation
  • Brings all pointers together into the index block: each file has its own index block — an array of disk-block addresses; the ith entry in the index block points to the ith block of the file; the directory contains the address of the index block. Allocation: when the file is created, all pointers in the index block are set to null; when the ith block is first written, a block is obtained from the free-space manager and its address is put in the ith index-block entry. Advantages: supports direct access (no external fragmentation); no size declaration needed. Disadvantages: wasted space for pointers (index block overhead is more than linked allocation: even a file of one or two blocks needs an entire index block — how large should the index block be? One block → minimal waste but a limit on file size)
  • Schemes to handle large files
    • Linked scheme: link several index blocks together (the last pointer of an index block is the address of the next index block, or null)
    • Multilevel index: a first-level index block points to a set of second-level index blocks, which in turn point to the file blocks. With 4,096-byte blocks and 4-byte pointers → 1,024 pointers per index block; two levels → 1,024 × 1,024 = 1,048,576 data blocks = 4 GB max file size; three levels → 4 TB
    • Combined scheme (UNIX inode): the first 15 pointers of the inode (in the FCB): 12 direct blocks, then single indirect, double indirect, triple indirect. With 4 KB blocks and 4-byte pointers: direct = 12 × 4 KB = 48 KB; single indirect = 1,024 × 4 KB = 4 MB; double = 1,024² × 4 KB = 4 GB; triple = 1,024³ × 4 KB = 4 TB; small files (≤ 48 KB) need no index block (fast); max file size ≈ 4 TB + 4 GB + 4 MB + 48 KB (but the 32-bit file-size field limits to 4 GB in many systems)

  • Performance: contiguous fits best for sequential and direct access with a single access to get a block (if the starting address is in memory); linked — best for sequential files (don't use for direct-access: the ith block might need i disk reads); some systems use contiguous for direct-access and linked for sequential access (declaring the access type at creation); indexed — performance depends on the index structure, the size of the file, and the position of the block; disk reading rates vs CPU (adding a few thousand instructions to save one disk access is worthwhile); storage-class-memory/NVM: no seeks, so different trade-offs. Block clustering improves throughput
Explanation

In contiguous allocation each file occupies consecutive blocks; the directory stores the start and the length, and block i is at b + i. This is simple and fast for both sequential and direct access, but it suffers from external fragmentation, and it is hard to know the size of a growing file. Extents, as in ext4, add another contiguous chunk when needed.

In linked allocation each block has a pointer to the next, and the directory has the first block. It has no external fragmentation and a file can grow, but only sequential access is efficient, the pointers use space (0.78% for 512-byte blocks with 4-byte pointers), and a lost pointer loses the rest of the file. The FAT variant keeps all the pointers in a table at the start of the volume. The directory holds the first block number, FAT[block] gives the next one, a special value marks the end and zero marks a free block. For the file starting at 217, FAT[217] = 618 and FAT[618] = 339, followed by the end marker, so the blocks are 217, 618, 339. Caching the FAT makes random access good.

In indexed allocation each file has an index block of pointers to its data blocks, so direct access is supported without external fragmentation, but the index block is an overhead, even for small files. For large files, the index blocks may be linked, or multilevel (with 4 KB blocks and 4-byte pointers, two levels give 4 GB and three levels 4 TB). The UNIX inode combines schemes: 12 direct pointers (48 KB), a single indirect (4 MB), a double indirect (4 GB) and a triple indirect (4 TB), so small files are quick to reach.
