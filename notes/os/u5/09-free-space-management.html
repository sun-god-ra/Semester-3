Free-Space Management

Operating Systems · Unit V: Storage Management and File System

Free-Space Management
Subject
Operating Systems (24CS204)
Unit
Unit V: Storage Management and File System
Topic
9 of 10
Terms
Linked list, Garbage collection, Inode, UNIX, LRU, System call, Copy-on-write

Practice: Part B questions for Unit V and Part A short questions.

Notebook notes
  • The file system maintains a free-space list to track available blocks/clusters; to create a file, search the free-space list for the required amount of space and allocate it to the new file (remove that space from the list); when a file is deleted, its space is added to the free-space list. (Free-space list may not be a list — a bit map or linked list etc.)
  • Bit vector (bit map): each block is represented by 1 bit: 1 = free, 0 = allocated (or reverse). Example: blocks 2, 3, 4, 5, 8, 9, 10, 11, 12, 13, 17 free, rest allocated → bit map 0011110011111100010…. Advantages: relatively simple and efficient to find the first free block or n consecutive free blocks (many computers have bit-manipulation instructions: find the first word that is not all 0s (all-zero word = all allocated); first 1 bit = first free block: block number = (number of bits per word) × (number of 0-value words) + offset of the first 1 bit). Disadvantage: bit map requires extra space: e.g. block size = 4 KB = 2¹² bytes, disk size = 2⁴⁰ bytes (1 TB) → n = 2⁴⁰/2¹² = 2²⁸ bits (= 32 MB) to track free blocks; if clusters of 4 blocks → 8 MB. Inefficient unless the entire vector is kept in main memory (and occasionally written to disk for recovery); possible only for smaller disks. Bit map must be updated consistently (bit changed on disk before the block is used)
  • Linked list (free list): link together all the free disk blocks, keeping a pointer to the first free block in a special location on the disk (and caching it in memory); each free block contains a pointer to the next free block. Example: free blocks 2, 3, 4, 5, 8, 9, 10, 11, 12, 13, 17, 18, 25, 26, 27 → head → block 2 → 3 → 4 → 5 → 8 → … Not efficient: to traverse the list, must read each block (substantial I/O time) — but traversing the free list is not frequent: normally the OS just needs a free block and uses the first one. FAT method incorporates free-block accounting into the allocation data structure (no separate method needed)
  • Grouping: a modification of the free-list approach: store the addresses of n free blocks in the first free block; the first n−1 of these are actually free; the last block contains the addresses of another n free blocks, and so on. Advantage: the addresses of a large number of free blocks can be found quickly (unlike the standard linked-list approach)
  • Counting: takes advantage of the fact that several contiguous blocks may be allocated or freed simultaneously (especially with contiguous allocation or clustering): keep the address of the first free block and the number n of free contiguous blocks that follow it; each entry in the free-space list = disk address + count; the overall list is shorter if counts are generally greater than 1; can be stored in a balanced tree (B-tree) for efficient lookup, insertion, deletion. Used in the Google file system
  • Space maps (ZFS): designed for huge file systems (exabytes); metaslabs — divide the device space into chunks (typically hundreds of them per device), each with its own space map; uses counting with a log-structured file-system idea: the space map is a log of all block activity (allocating, freeing) in time order, in counting format; when ZFS decides to allocate or free space from a metaslab, it loads the associated space map into memory in a balanced-tree structure (indexed by offset), replays the log into that structure, and updates it; the in-memory space map is then an accurate representation of the allocated and free space in the metaslab; ZFS condenses the map as much as possible by combining contiguous free blocks into a single entry; finally the free-space list is updated on disk
  • TRIM (SSDs, NVM): since NVM flash cannot overwrite and blocks need to be erased before writing, the file system informs the device that blocks are unused (TRIM) so the device can erase them ahead of time for faster writes (and garbage collection)
  • Efficiency and performance: efficiency depends on the disk-allocation and directory algorithms (e.g., UNIX inodes preallocated on a partition; cluster blocks; the type of data kept in a file's directory entry such as "last access time" updates → write for each read, so disable "access time" updates (noatime); fixed-size vs variable-size pointer structures; 32-bit vs 64-bit pointers — a trade-off between max file size and space). Performance — buffer cache (separate section of main memory for frequently used blocks), page cache (caches pages rather than disk blocks using virtual-memory techniques and addresses; memory-mapped I/O uses a page cache; routine I/O through the file system uses the buffer cache → double caching problem; a unified buffer cache uses the same page cache to cache both memory-mapped pages and ordinary file-system I/O to avoid double caching); synchronous writes (no buffering — e.g. metadata) vs asynchronous writes (stored in cache and return immediately — common); free-behind and read-ahead techniques for sequential access (free-behind — remove a page from the buffer as soon as the next page is requested; read-ahead — a requested page and several subsequent pages are read and cached); LRU replacement is not best for sequential access → free-behind/read-ahead
  • Recovery: because files and directories are kept both in main memory and on disk, a system failure might cause data loss and inconsistency. Consistency checking (fsck in UNIX, chkdsk in Windows) — compares data in the directory structure with the data blocks on disk and tries to fix inconsistencies (allocation algorithms and free-space management algorithms dictate what types of problems the checker can find, e.g. with linked allocation, a loss of a link may result in data loss). Log-structured (journaling) file systems: all changes to metadata are written sequentially to a log (journal) as transactions; once the changes are written to the log, they are considered committed and the system call can return; the log entries are replayed asynchronously to the file system structures; when the entire committed transaction has been completed, the entry is removed from the log; on a crash, transactions in the log that were committed but not completed are completed, and uncommitted transactions are undone — fast recovery (ext3/ext4, NTFS, ZFS, XFS, JFS). Other solutions: backup and restore — full backup and incremental backup; snapshots (ZFS), WAFL (Write-Anywhere File Layout of NetApp) — never overwrite blocks, take snapshots by copying the root inode; copy-on-write
Explanation

A bit vector has one bit for each block (1 for free, here). It is simple, and finding the first free block or n consecutive free blocks is fast with bit instructions, but it takes space: a 1 TB disk with 4 KB blocks has 2²⁸ blocks and needs 32 MB. A linked list links all the free blocks, which is simple but slow to traverse. Grouping stores the addresses of n free blocks in the first free block, so many addresses can be found at once. Counting stores the address of the first free block and the number of contiguous free blocks that follow. ZFS uses space maps, which are logs of block activity in counting format, per metaslab. TRIM tells the SSD which blocks are no longer used.

Performance is improved by caches (buffer cache and page cache; a unified buffer cache avoids double caching), read-ahead and free-behind for sequential access. For recovery, the consistency checker (fsck) compares the directories with the data blocks. Journaling (log-structured) file systems write the metadata changes to a log as transactions first. After a crash, the committed transactions are replayed and the uncommitted ones are undone. Backups (full and incremental) and snapshots also help.
