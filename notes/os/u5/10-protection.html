Protection

Operating Systems · Unit V: Storage Management and File System

Protection
Subject
Operating Systems (24CS204)
Unit
Unit V: Storage Management and File System
Topic
10 of 10
Terms
Semaphore, IPC, UNIX, Protection ring, Kernel, Access matrix, JVM

Practice: Part B questions for Unit V and Part A short questions.

Notebook notes
  • Protection = mechanism for controlling access of programs, processes, or users to the resources defined by a computer system; security = defence against external and internal attacks. In the protection discussion, OS provides mechanisms; policy decided by users/administrators
  • Goals of protection: to prevent malicious misuse (deliberate violation of access restriction by a user); to ensure that each program component active in a system uses system resources only in ways consistent with stated policies (reliability — detecting latent errors at the interfaces between component subsystems, early detection of errors); to provide a means to distinguish between authorised and unauthorised usage. Protection is a mechanism/policy separation
  • Principles of protection: the guiding principle is the principle of least privilege — programs, users, and systems should be given just enough privileges to perform their tasks; limits damage if the entity has a bug, gets abused; can be static (during the life of the system, during the life of a process) or dynamic (changed by the process as needed — domain switching, privilege escalation); "need to know" — a similar concept for objects (e.g. sudo in Unix); fine-grained (more complex, more overhead, more protective) vs coarse-grained (simpler, less protective); audit trails; compartmentalisation; "Is it better to give everything to a few or little to many?" — apply least privilege; a user should use a normal account for everyday work and a privileged account only when needed (separate user accounts for different activities)
  • Domain of protection
    • A computer system is a collection of processes and objects. Objects: hardware objects (CPU, memory segments, printers, disks, tape drives) and software objects (files, programs, semaphores); each has a unique name and a finite set of operations that can be performed on it (CPU → execute; memory segments → read, write; CD-ROM → read only; tape drives → read, write, rewind; data files → create, open, read, write, close, delete; program files → read, write, execute, delete)
    • Need to know principle: a process should be allowed to access only those resources for which it has authorisation and which it currently requires to complete its task
    • Domain structure: a domain = set of access rights; access right = <object-name, rights-set> (rights-set = subset of all valid operations on the object). Association between a process and a domain can be static (the set of resources available to a process is fixed over its lifetime) or dynamic (domain switching). Domain can be realised as: each user (the set of objects accessible depends on the identity of the user; domain switching when the user changes — logout/login), each process (depends on the process's identity; domain switching corresponds to IPC — message sent from one process to another), each procedure (depends on the local variables defined within the procedure; domain switching when a procedure call is made)
    • UNIX domain — domain = user-id; domain switch accomplished via the file system: each file has an owner attribute and a domain bit (setuid bit). When a user executes a file with the setuid bit on, the user-id is set to the owner of the file being executed; when execution completes, the user-id is reset. Example: the passwd command is setuid root so ordinary users can change their own password entry in a protected file. Android uses application IDs (AID) — each app has a unique user ID
    • Protection rings (MULTICS): domains are organised hierarchically into rings — ring 0 is the kernel (most privileged), ring N the least privileged; Ring_i ⊆ Ring_j (rings are nested): if j < i, then D_j has all the privileges of D_i; ring switching via gates (call a gate instruction) to a more privileged ring (ring-crossing); the processor tracks the current ring number; Intel processors use four rings (0–3); ARM uses TrustZone (TZ) with kernel and secure monitor modes (exception levels EL0–EL3); Intel SGX (enclaves). MULTICS: 8 rings; rings help protect against (but don't completely solve) privilege escalation. Disadvantage: ring structure doesn't allow need-to-know (a process in an outer ring may not have access to a subset of the objects accessible in an inner ring unless they have rights to all) — more flexible: capability-based
  • Access matrix — view protection as a matrix: rows represent domains, columns represent objects; Access(i, j) = the set of operations that a process executing in Domain_i can invoke on Object_j
domain \ object F1 F2 F3 Printer
D1 read read
D2 print
D3 read execute
D4 read, write read, write
  • Use of access matrix: if a process in Domain D_i tries to do operation op on object O_j, then op must be in the access matrix; the matrix can be expanded to dynamic protection — operations to add, delete access rights; special access rights: owner of O_i, copy op from O_i to O_j (denoted by *: copy of the right can be limited: copy (copy right with * to another domain in the same column), transfer (original right removed), limited copy (only the right without * gets copied — no further propagation)), control — D_i can modify D_j's access rights (applies to domain objects, a row), switch — a process executing in D_i can switch to D_j (a domain-object column entry)
    • Domain switch is added as objects — the columns of domains (e.g., D1 switch → D2). Copy (*), owner (can add/delete rights in the column — object), control (can remove rights in the row — domain) — help to solve the confinement problem (a process cannot leak info); the access matrix design separates mechanism from policy: mechanism — OS provides the access matrix + rules, ensuring that the matrix is manipulated only by authorised agents and rules strictly enforced; policy — user dictates the policy (who can access what object and in what mode)
    • Implementation of the access matrix: a sparse matrix, so storing it as a table is wasteful. Options
      • Global table: a set of ordered triples <domain, object, rights-set>; table can be large (won't fit in main memory); difficult to group objects (e.g. an object that everyone can read must have an entry for each domain)
      • Access lists for objects (ACL): each column implemented as an access list for one object: list of ordered pairs <domain, rights-set> defining all domains with a nonempty set of access rights for the object; default set of rights for all other domains; easy to match with the user's concept of the object (users create an object and specify who can access it); used by most OSes (Windows, Linux, macOS); getfacl/setfacl. Disadvantage: determining the set of access rights for each domain is difficult (finding which domains can access an object is easy; finding all objects accessible to a domain requires searching all ACLs); the lists can be long and time-consuming to search at each access
      • Capability lists for domains: each row = a capability list for a domain — list of objects together with the operations allowed on them; an object is represented by its name or address, called a capability; to execute an operation M on an object O_j, the process executes the operation M, specifying the capability for O_j as a parameter — possession of the capability = access allowed. The capability list is associated with a domain but never directly accessible by a process executing in that domain (it's a protected object, maintained by the OS); capabilities are distinguished from other data (tagged or in the OS address space); Cambridge CAP, Hydra; good for localising information for a given process; but revocation is difficult
      • Lock–key mechanism: a compromise between ACL and capability lists: each object has a list of unique bit patterns, called locks; each domain has a list of unique bit patterns, called keys; a process in a domain can access an object only if that domain has a key that matches one of the locks of the object; the key list must be managed by the OS on behalf of the domain (users not allowed to examine or modify the lists)
      • Comparison: ACLs — efficient revocation (just delete the entry), object-centric; capabilities — efficient for a process checking its own access (no list search), but revocation difficult; many systems use a combination — ACL in the file system when opened + a capability (file descriptor/handle) returned to the process for subsequent accesses: access list searched at open(); the file descriptor is a capability and close destroys it
  • Revocation of access rights — (immediate vs delayed, selective vs general, partial vs total, temporary vs permanent). ACL: simple — search the access list and remove the right; capabilities: more difficult: reacquisition (periodically delete capabilities, processes must reacquire; the revoked ones can't), back-pointers (each object keeps a list of pointers to all capabilities — MULTICS), indirection (capabilities point indirectly to objects through a global table — remove entries from the table; no selective revocation), keys (a master key associated with the object; a capability is created with the master key as its key; replace the master key to revoke — selective revocation not supported unless several keys)
  • Role-based access control (RBAC): privileges are assigned to roles; users are assigned roles; Solaris 10+: a role is enabled via password; least privilege; setuid is replaced by roles/privileges. Mandatory access control (MAC) (labels — SELinux, Trusted Solaris; Windows Vista mandatory integrity control), vs discretionary access control (DAC) (owner decides — UNIX file permissions). Language-based protection — protection enforced by the compiler/runtime (e.g., Java's JVM type safety, stack inspection, sandboxing; security manager); more fine-grained than OS-enforced protection. Capability-based systems (Linux capabilities: CAP_NET_ADMIN etc. split root into capabilities); system-call filtering (seccomp); sandboxing; code signing; ASLR (address-space layout randomisation)
Explanation

Protection controls the access of processes and users to the resources of the system. Its goals are to prevent misuse and to ensure that each program uses resources only in ways that agree with the policy. The guiding principle is least privilege: give a program or user only the rights needed to do its task, so that the damage is limited if something goes wrong. The related need-to-know principle says that a process should access only the resources it needs at the moment.

A domain is a set of access rights, each right being an <object, rights-set> pair. A domain can be a user, a process or a procedure. In UNIX the domain is the user id, and the setuid bit lets a program run as its owner; passwd is the standard example. In protection rings, the domains are nested, with ring 0 being the kernel and the most privileged, and a gate is used to cross to a more privileged ring. Rings do not allow need-to-know access.

The access matrix has the domains as rows and the objects as columns, with Access(i, j) being the operations that a process in domain i can perform on object j. Special rights are copy (marked with *, with copy, transfer and limited copy versions), owner, control (modify a domain's rights) and switch (move to another domain). The matrix is sparse and is implemented as a global table of triples, as access lists for each object (the columns, used by most OSes, easy for users, but searching is slow and finding all objects of a domain is hard), as capability lists for each domain (the rows; possession of a capability gives access, and the list is protected by the OS, but revocation is difficult), or as a lock-key scheme that lies between the two. Real systems combine them: the ACL is checked at open(), and the file descriptor then acts as a capability.

Revocation is easy with ACLs, since the entry is deleted. With capabilities it needs reacquisition, back-pointers, indirection through a global table or keys. Role-based access control assigns privileges to roles. Mandatory access control uses labels (SELinux), unlike discretionary access control, where the owner decides (UNIX permissions). Language-based protection (Java's type safety and the sandbox) enforces access in the language run time.
