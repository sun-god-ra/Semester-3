Operating Systems · Unit II: Process Management and Scheduling

Multithreading Models
Subject
Operating Systems (24CS204)
Unit
Unit II: Process Management and Scheduling
Topic
6 of 14
Terms
Kernel, System call, Multiprocessor, UNIX, POSIX, JVM

Practice: Part B questions for Unit II and Part A short questions.

Notebook notes
  • Support for threads — user threads (above the kernel, managed without kernel support by a thread library) and kernel threads (supported and managed directly by the OS: Windows, Linux, macOS, Solaris, iOS, Android). A relationship must exist between user threads and kernel threads
Model Mapping Pros Cons
Many-to-One many user threads → one kernel thread efficient, thread management in user space entire process blocks if one thread makes a blocking system call; no parallelism on multicore (only one thread in the kernel at a time). Ex: Solaris Green threads, GNU Portable Threads (rare today)
One-to-One each user thread → one kernel thread more concurrency (another thread runs when one blocks), parallel on multiprocessors overhead of creating a kernel thread per user thread, limits number of threads. Ex: Linux, Windows, macOS
Many-to-Many many user threads → smaller or equal number of kernel threads flexible; no limit on user threads, kernel can schedule others if one blocks hard to implement. Ex: Windows with ThreadFiber package, older Solaris
Two-level many-to-many + one-to-one bind of specific user thread to a kernel thread allows both complex. Ex: IRIX, HP-UX, Tru64 UNIX, Solaris 8
  • Thread libraries provide the programmer an API for creating and managing threads: POSIX Pthreads (user- or kernel-level; specification, not implementation; pthread_create, pthread_join), Windows threads (kernel-level; CreateThread), Java threads (managed by the JVM; implemented using the host's native thread library; Thread class or Runnable interface; start() → run())
  • Implicit threading — design of programs with hundreds or thousands of threads: the compilers and run-time libraries (not programmers) create and manage threads: thread pools (create a number of threads at start-up, in a pool where they wait for work → faster servicing, bound on number of threads), fork–join (parent forks children then joins; Java ForkJoinPool), OpenMP (#pragma omp parallel), Grand Central Dispatch (GCD) (Apple; dispatch queues — serial and concurrent), Intel Threading Building Blocks (TBB)
  • Threading issues: fork() and exec() semantics (does fork() duplicate all threads or only the calling thread? exec() replaces the entire process, including all threads); signal handling (signal = notification of event; synchronous (illegal memory access, division by zero — delivered to the same process that caused it) vs asynchronous (Ctrl+C, timer expiry — delivered to another process); handled by default handler or user-defined handler; deliver to the thread to which the signal applies, to every thread, to certain threads, or to a designated thread); thread cancellation (asynchronous — terminates the target immediately; deferred — target periodically checks whether it should terminate, at cancellation points); thread-local storage (TLS) (each thread has its own copy of some data — unlike local variables, visible across function invocations); scheduler activations (upcalls from the kernel to the upcall handler in the thread library, using an LWP (lightweight process) — an intermediate data structure between user and kernel threads, appearing as a virtual processor)
  • Linux threads: clone() system call with flags (CLONE_FS, CLONE_VM, CLONE_SIGHAND, CLONE_FILES) decides how much is shared between parent and child; Linux uses the term task for process or thread; fork() = clone() with no sharing flags
Explanation

User threads are managed by a library, kernel threads by the OS. In the many-to-one model, many user threads map to one kernel thread: it is efficient, but one blocking call blocks all and there is no parallelism. In the one-to-one model, each user thread has its own kernel thread, which gives more concurrency but costs more, so the number of threads is limited (Linux, Windows). In the many-to-many model, many user threads map to the same or a smaller number of kernel threads; it is flexible but difficult to implement.

Implicit threading lets compilers and libraries manage threads: thread pools, fork-join, OpenMP and Grand Central Dispatch. Threading issues are the meaning of fork() and exec() in a multithreaded program, signal handling (synchronous signals go to the thread that caused them, asynchronous ones, such as Ctrl-C, go elsewhere), thread cancellation (asynchronous, or deferred at cancellation points), thread-local storage and scheduler activations (upcalls from the kernel to the library through LWPs). Linux creates a thread and a process using the same clone() call, and flags tell how much is shared.
