Interprocess Communication (IPC)

Operating Systems · Unit II: Process Management and Scheduling

Interprocess Communication (IPC)

On this page
  1. Shared-memory systems
  2. Message-passing systems
Notebook notes
  • Processes may be independent (cannot affect or be affected by others, share no data) or cooperating. Reasons for cooperation: information sharing, computation speedup, modularity, convenience
  • Cooperating processes need IPC: two fundamental models — shared memory and message passing
Shared memory Message passing
Communication via a region of memory both processes map send/receive system calls
Speed faster — system calls only to set up the region; after that memory-speed slower — kernel intervention each time
Good for large amounts of data smaller amounts, easier (no conflicts), good between computers
Synchronisation user's responsibility (e.g. don't write at the same location) OS handles
Cache coherence issue on multicore yes (more costly) less
Shared-memory systems
  • A process creates a shared-memory segment in its address space; other processes attach it to their address space. Normally the OS prevents a process from accessing another's memory — they must agree to remove this restriction. The form of data and location are determined by the processes, not the OS
  • Producer–consumer problem (paradigm for cooperating processes): producer produces information, consumer consumes it; a buffer is shared. Unbounded buffer (no limit; consumer may wait; producer never waits) vs bounded buffer (fixed size; consumer waits if empty; producer waits if full)
  • Bounded-buffer solution using a circular array with in (next free position) and out (first full position): buffer empty when in == out; full when ((in + 1) % BUFFER_SIZE) == out — this uses at most BUFFER_SIZE − 1 items
c
#define BUFFER_SIZE 10
typedef struct { /* ... */ } item;
item buffer[BUFFER_SIZE];
int in = 0, out = 0;

/* producer */
while (true) {
    item next_produced = /* ... */;
    while (((in + 1) % BUFFER_SIZE) == out) ;   /* do nothing: full */
    buffer[in] = next_produced;
    in = (in + 1) % BUFFER_SIZE;
}
/* consumer */
while (true) {
    while (in == out) ;                          /* do nothing: empty */
    item next_consumed = buffer[out];
    out = (out + 1) % BUFFER_SIZE;
}
  • POSIX shared memory: shm_open() → ftruncate() (set size) → mmap() (map into address space) → write/sprintf → munmap, shm_unlink()
Message-passing systems
  • Mechanism for processes to communicate and synchronise their actions without sharing the same address space; useful in a distributed environment. Two operations: send(message) and receive(message). Message size fixed or variable
  • If P and Q want to communicate, they need a communication link — physical (shared memory, hardware bus, network) or logical (direct/indirect, synchronous/asynchronous, automatic/explicit buffering)
  • Naming
    • Direct communication: processes name each other explicitly: send(P, message), receive(Q, message). Symmetric addressing (both sender and receiver name the other) vs asymmetric (only sender names the recipient: receive(id, message) — receives from any process). Link is established automatically; exactly one link per pair; link is associated with exactly two processes. Disadvantage: limited modularity — changing a process identifier requires finding all references
    • Indirect communication: messages are sent to and received from mailboxes (ports); each mailbox has a unique id; processes communicate only if they share a mailbox; send(A, message), receive(A, message). A link may be associated with more than two processes; each pair may have several links. Mailbox ownership: by a process (owner receives; disappears when the owner terminates) or by the OS (independent; OS provides operations to create, send/receive, delete). Who receives when multiple receivers? allow a link on at most two processes; allow only one process at a time to execute receive; or let the system select the receiver arbitrarily
  • Synchronisation: message passing may be blocking (synchronous) or nonblocking (asynchronous): blocking send — sender blocked until message received; nonblocking send — sender sends and continues; blocking receive — receiver blocks until message available; nonblocking receive — receiver gets a valid message or null. When both send and receive are blocking = rendezvous
  • Buffering: messages exchanged reside in a temporary queue: zero capacity (no buffering, sender must block until receiver receives — rendezvous), bounded capacity (finite length n; sender blocks if link full), unbounded capacity (infinite; sender never blocks)
  • Examples of IPC systems: POSIX shared memory, Mach message passing (mailboxes called ports; system calls msg_send, msg_receive, msg_rpc; bootstrap port; kernel task self port, notify port), Windows (advanced local procedure call (ALPC) — connection port and communication port, 3 techniques: small messages via port's message queue, larger via section object, huge via callback), pipes
  • Pipes: one of the first IPC mechanisms in UNIX. Issues: unidirectional or bidirectional? half-duplex or full-duplex? relationship (parent–child) needed? over a network?
    • Ordinary pipes: producer writes to one end (write end), consumer reads from the other (read end); unidirectional, cannot be accessed from outside the process that created it; typically a parent creates a pipe and uses it to communicate with a child it creates via fork(). pipe(int fd[2]) — fd[0] is the read end, fd[1] is the write end; Windows calls them anonymous pipes
    • Named pipes (FIFOs): bidirectional (in Windows; half-duplex in UNIX); no parent–child relationship necessary; continue to exist after the communicating processes finish; several processes can use it; UNIX mkfifo(); shell ls | wc -l
  • Client–server communication: sockets (an endpoint for communication, identified by IP address + port number, e.g. 161.25.19.8:1625; well-known ports below 1024: 22 ssh, 23 telnet, 80 HTTP, 443 HTTPS, 21 FTP; 127.0.0.1 = loopback), remote procedure calls (RPC) (abstracts procedure calls between processes on networked systems; stubs (client-side proxy; marshalling parameters); XDR external data representation; matchmaker daemon), pipes
Explanation

Cooperating processes need IPC for information sharing, speed-up, modularity and convenience. There are two models. In shared memory, a region of memory is mapped into the address space of both processes. This is fast, because after the setup no kernel call is needed, but the processes must make sure by themselves that they do not write the same place at the same time. In message passing, the processes use send and receive, which are slower because of the kernel but easier to use, and which work between computers.

The producer-consumer problem is the standard example: a producer puts items in a shared buffer and a consumer takes them out. With a circular bounded buffer, in is where the next item goes and out is where the next item comes from. The buffer is empty when in equals out and is full when (in+1) mod size equals out. It therefore holds at most size−1 items.

Message passing can name processes directly (send(P, m), receive(Q, m)) or use mailboxes (ports), where processes communicate if they share a mailbox. Direct communication has limited modularity, because changing a process id requires changes in every reference. Sending and receiving may be blocking or non-blocking. If both are blocking, it is called a rendezvous. The buffer may have zero capacity, bounded capacity, or unbounded capacity.

An ordinary pipe is a one-way channel between a parent and a child; fd[0] is the read end and fd[1] is the write end. It disappears when the processes end. A named pipe (FIFO) has a name in the file system, needs no parent-child relation, and remains after the processes end. Sockets are endpoints of communication, identified by IP address and port number. RPC lets a process call a procedure in another machine; a stub on the client marshals the parameters.
