Monitors

Operating Systems · Unit III: Process Synchronization and Deadlocks

Monitors
Subject
Operating Systems (24CS204)
Unit
Unit III: Process Synchronization and Deadlocks
Topic
8 of 15
Terms
Semaphore, Mutual exclusion, Deadlock, Abstraction, Dining philosophers, Starvation, FCFS, Race condition, Swapping

Practice: Part B questions for Unit III and Part A short questions.

Notebook notes
  • Problem with semaphores: timing errors can occur if semaphores are used incorrectly — e.g. signal(mutex) … wait(mutex) (several processes in CS → violates mutual exclusion); wait(mutex) … wait(mutex) (deadlock); omitting wait(mutex) or signal(mutex) or both (mutual exclusion violated or permanent block). Hard to detect (occur only with particular sequences)
  • Monitor = high-level abstraction (an abstract data type, ADT) that provides a convenient and effective mechanism for process synchronisation: internal variables only accessible by code within the procedures; only one process may be active within the monitor at a time (mutual exclusion is automatic, the programmer need not code it)
monitor monitor_name {
    /* shared variable declarations */
    function P1 ( . . . ) { . . . }
    function P2 ( . . . ) { . . . }
    initialization_code ( . . . ) { . . . }
}
  • Condition variables condition x, y; — two operations: x.wait() — the process that invokes it is suspended until another process invokes x.signal(), which resumes exactly one suspended process (if no process suspended, signal() has no effect — unlike semaphore signal, which always changes the value)
  • Signal-and-wait: if Q is waiting on x and P calls x.signal(): P waits until Q leaves the monitor (or waits for another condition). Signal-and-continue: Q waits until P leaves the monitor (or waits). Concurrent Pascal used a compromise: P executes signal and immediately leaves
  • Dining philosophers with a monitor — states THINKING, HUNGRY, EATING; philosopher i can set state[i] = EATING only if both neighbours are not eating; condition self[5]. Operations pickup(i), putdown(i), test(i). Deadlock-free, but starvation is possible
monitor DiningPhilosophers {
    enum {THINKING, HUNGRY, EATING} state[5];
    condition self[5];

    void pickup(int i) {
        state[i] = HUNGRY;
        test(i);
        if (state[i] != EATING) self[i].wait();
    }
    void putdown(int i) {
        state[i] = THINKING;
        test((i + 4) % 5);
        test((i + 1) % 5);
    }
    void test(int i) {
        if (state[(i + 4) % 5] != EATING && state[i] == HUNGRY &&
            state[(i + 1) % 5] != EATING) {
            state[i] = EATING;
            self[i].signal();
        }
    }
    initialization_code() {
        for (int i = 0; i < 5; i++) state[i] = THINKING;
    }
}
/* each philosopher: DiningPhilosophers.pickup(i); eat; DiningPhilosophers.putdown(i); */
  • Implementing a monitor with semaphores: mutex (1) for entry; next (0) on which signalling processes suspend; next_count; for each condition x: x_sem (0) and x_count. Each procedure F is wrapped: wait(mutex); body; if (next_count > 0) signal(next); else signal(mutex);. x.wait(): x_count++; if (next_count > 0) signal(next); else signal(mutex); wait(x_sem); x_count--;. x.signal(): if (x_count > 0) { next_count++; signal(x_sem); wait(next); next_count--; }
  • Resuming processes within a monitor: if several processes are suspended on condition x and x.signal() is executed — FCFS or conditional-wait x.wait(c) where c is a priority number, resumed in order of the smallest c. Example: ResourceAllocator monitor (R.acquire(t), R.release()), where t is the maximum time the process plans to use the resource
  • Java monitors: every object has a single lock; a method declared synchronized acquires it; wait() / notify() / notifyAll() on an object; reentrant locks, condition variables; semaphores (java.util.concurrent.Semaphore)
  • Other approaches: transactional memory, OpenMP (#pragma omp critical), functional programming languages (no mutable state → no race conditions)
Explanation

Semaphores are easy to misuse: swapping wait and signal, or omitting one, breaks mutual exclusion or deadlocks, and such errors appear only in certain interleavings. A monitor is a language-level construct, an abstract data type in which the shared data is accessible only through the monitor's procedures, and only one process can be active inside at a time, automatically. For waiting for a condition it uses condition variables with x.wait(), which suspends the process, and x.signal(), which resumes one suspended process and has no effect if none is waiting (unlike a semaphore signal, which is remembered). When a process P signals and a process Q is resumed, either P waits (signal-and-wait) or Q waits (signal-and-continue).

In the monitor solution for dining philosophers, a philosopher is thinking, hungry or eating, and may eat only if neither neighbour is eating, so a deadlock cannot occur, though starvation still can. Java gives each object a lock for synchronized methods, and wait(), notify() and notifyAll().
