Deadlock Detection

Operating Systems · Unit III: Process Synchronization and Deadlocks

Deadlock Detection
Subject
Operating Systems (24CS204)
Unit
Unit III: Process Synchronization and Deadlocks
Topic
14 of 15
Terms
Deadlock, Starvation

Practice: Part B questions for Unit III and Part A short questions.

Notebook notes
  • If the system uses neither prevention nor avoidance, it must provide an algorithm to examine the state (detection) and an algorithm to recover
  • Single instance of each resource type: use a wait-for graph — remove the resource nodes from the RAG and collapse the edges: \(P_i\to P_j\) if \(P_i\) is waiting for a resource held by \(P_j\). Deadlock ⇔ a cycle in the wait-for graph. Periodically invoke a cycle-detection algorithm — \(O(n^2)\) (\(n\) = number of vertices)
  • Several instances of a resource type: wait-for graph is not applicable; use an algorithm similar to Banker's with data structures Available[m], Allocation[n][m], Request[n][m] (Request[i][j] = k → Pi is requesting k more instances of Rj)
    1. Work = Available; for all \(i\): Finish[i] = false if Allocation_i ≠ 0, else true (a process holding nothing cannot be involved)
    2. Find \(i\) with Finish[i] == false and Request_i ≤ Work; if none → 4
    3. Work += Allocation_i; Finish[i] = true; go to 2
    4. If Finish[i] == false for some i → system is in deadlock, and Pi is deadlocked. Complexity \(O(m\times n^2)\) - Optimistic assumption: a process whose request can be satisfied will return its resources (no further request) — if it later requests more, a deadlock may be detected on the next run - Example: 5 processes; A (7), B (2), C (6): Allocation P0 (0,1,0), P1 (2,0,0), P2 (3,0,3), P3 (2,1,1), P4 (0,0,2); Request P0 (0,0,0), P1 (2,0,2), P2 (0,0,0), P3 (1,0,0), P4 (0,0,2); Available (0,0,0). Sequence ⟨P0, P2, P3, P1, P4⟩ gives Finish all true → no deadlock. If P2 requests an additional C instance (Request₂ = (0,0,1)) → P0 can finish (Work = (0,1,0)), but then no one else's request can be met → P1, P2, P3, P4 deadlocked
  • Detection-algorithm usage: when and how often? depends on how often a deadlock is likely to occur and how many processes will be affected. Invoke whenever a request cannot be granted immediately (identifies exact set of deadlocked processes and the process that "caused" it; but considerable overhead), or periodically (e.g. once per hour) or when CPU utilisation drops below 40 %. If invoked at arbitrary points, there may be many cycles in the graph and we cannot tell which process "caused" the deadlock
Explanation

If a system uses neither prevention nor avoidance, it has to detect deadlocks. With one instance of each resource, it builds a wait-for graph by removing the resource nodes of the allocation graph, and a cycle means deadlock. With several instances, it uses an algorithm like the Banker's, with Allocation and Request, and any process that cannot finish is deadlocked. It assumes optimistically that a process whose request can be satisfied will finish and release its resources. The algorithm can be run on each request that cannot be granted immediately, which has a large overhead, or periodically, or when CPU utilisation falls below about 40%.

Recovery is by process termination (abort all deadlocked processes, or one at a time until the cycle is broken, choosing by priority, run time, resources, and so on) or by resource preemption, which needs a choice of victim, rollback to a safe state, and a guarantee against starvation, by counting rollbacks in the cost.
