Peterson's Solution

Operating Systems · Unit III: Process Synchronization and Deadlocks

Peterson's Solution
Subject
Operating Systems (24CS204)
Unit
Unit III: Process Synchronization and Deadlocks
Topic
3 of 15
Terms
Critical section, Mutual exclusion, Peterson's solution

Practice: Part B questions for Unit III and Part A short questions.

Notebook notes
  • Classic software-based solution for two processes (P0 and P1; \(i\) and \(j=1-i\)) that alternate execution between critical and remainder sections. Assumes load and store instructions are atomic (cannot be interrupted)
  • Shared variables: int turn; — whose turn it is to enter the critical section; boolean flag[2]; — flag[i] = true means Pi is ready to enter
c
/* process Pi */
do {
    flag[i] = true;          /* I want to enter */
    turn = j;                /* but let the other go first */
    while (flag[j] && turn == j)
        ;                    /* busy wait */
    /* critical section */
    flag[i] = false;
    /* remainder section */
} while (true);
  • Proof that it satisfies the three requirements
    1. Mutual exclusion: each Pi enters its CS only if either flag[j] == false or turn == i. If both were in CS, flag[0] == flag[1] == true, so they must have passed the while at about the same time; but turn can be only 0 or 1, so only one of them could pass → mutual exclusion preserved
    2. Progress and 3. Bounded waiting: Pi can be prevented from entering only if stuck in the while with flag[j] == true and turn == j. If Pj is not ready, flag[j] false → Pi enters. If Pj is ready and executing, it will set turn = i after finishing (and sets flag[j]=false), so Pi enters after at most one entry by Pj → bounded waiting (waits at most 1 turn)
  • Why it may fail on modern architectures: processors and compilers may reorder reads and writes that have no dependencies (for single-threaded performance), so flag[i] = true; turn = j; may be reordered → both enter. Needs memory barriers. So Peterson's is not guaranteed to work on modern hardware; it is a good algorithmic description only
  • Memory models: strongly ordered (a memory modification on one processor is immediately visible to all others) vs weakly ordered (modifications may not be immediately visible). Memory barrier (fence) — instruction that forces any change in memory to be propagated (made visible) to all other processors; ensures all loads and stores complete before subsequent ones
Explanation

Peterson's solution works for two processes, with a turn variable and a flag[2] array. A process sets its own flag, which says "I want to enter", and then gives the turn to the other process ("you go first"). It then waits while the other process wants to enter and it is the other's turn. Since turn has only one value, only one of the two can pass the loop when both want to enter. If the other does not want to enter, the flag is false, and the process enters at once. If it does want to, then after it finishes it clears its flag, and so the waiting process enters after at most one turn of the other, which is bounded waiting. The solution is correct as an algorithm but may fail on modern processors, because the compiler or CPU can reorder the independent store instructions, so memory barriers are needed in real code.
