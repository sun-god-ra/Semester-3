Deadlock Prevention

Operating Systems · Unit III: Process Synchronization and Deadlocks

Deadlock Prevention
Subject
Operating Systems (24CS204)
Unit
Unit III: Process Synchronization and Deadlocks
Topic
12 of 15
Terms
Mutual exclusion, Mutex, Deadlock, Starvation, Semaphore, Swapping, Operating system

Practice: Part B questions for Unit III and Part A short questions.

Notebook notes
  • Ensure that at least one of the four necessary conditions cannot hold
    • Mutual exclusion: not required for sharable resources (read-only files); must hold for nonsharable (a mutex lock) — we cannot generally prevent deadlocks by denying mutual exclusion
    • Hold and wait: guarantee that whenever a process requests a resource, it does not hold any other resources — protocol 1: require the process to request and be allocated all its resources before execution begins; protocol 2: allow a process to request resources only when it has none (release all before requesting more). Disadvantages: low resource utilisation (resources allocated but unused for a long time), starvation possible (a process needing several popular resources may wait forever)
    • No preemption: if a process holding resources requests another that cannot be immediately allocated, all resources it currently holds are preempted (released implicitly), and added to its waiting list; the process is restarted only when it can regain its old resources and the new ones. Alternative: if a requested resource is held by a process that is itself waiting, preempt it and give it to the requester. Applicable to resources whose state can be saved and restored (CPU registers, memory space); not to mutex locks and semaphores
    • Circular wait: impose a total ordering of all resource types and require each process to request resources in an increasing order of enumeration — \(F: R\to N\); a process holding \(R_i\) may request \(R_j\) only if \(F(R_j) > F(R_i)\) (or must release all \(R_i\) with \(F(R_i)\ge F(R_j)\) first). Proof by contradiction: circular wait means \(F(R_0)<F(R_1)<\dots<F(R_n)<F(R_0)\), impossible. Lock ordering is an application responsibility (Witness in FreeBSD verifies); dynamic locks (e.g. a function transaction(from, to) swapping accounts) can defeat the ordering → order by account number
Explanation

There are three ways of dealing with deadlocks: prevention or avoidance, detection and recovery, or ignoring the problem (the ostrich algorithm), which is what most operating systems actually do, as deadlocks are rare.

Prevention removes one of the four conditions. Mutual exclusion cannot be removed for resources that are inherently non-sharable. Hold and wait can be removed by requiring a process to ask for all resources at once or to hold none while asking, but this wastes resources and can starve. No preemption can be removed by taking away the resources held by a process that must wait, which suits resources whose state is easy to save (CPU registers, memory) but not locks. Circular wait can be removed by numbering all the resource types and requiring the processes to request in increasing order, so no cycle can form.
