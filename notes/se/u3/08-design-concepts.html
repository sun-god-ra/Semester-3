Notebook notes
Concept Meaning
Abstraction concentrate on essential, ignore detail. Procedural abstraction (named sequence of instructions — "open door"), data abstraction (named collection of data — "door": type, dimensions, weight…)
Architecture overall structure of the software; the way components interact; structural properties, extra-functional properties, families of related systems
Patterns named nugget of insight conveying the essence of a proven solution to a recurring problem within a certain context
Separation of concerns a problem is easier to solve if split into pieces (concerns), each solved independently. Divide and conquer
Modularity software divided into separately named, addressable components (modules) that are integrated to satisfy requirements. Cost: effort to develop each module decreases with more modules, but integration cost increases → optimum number of modules
Information hiding modules specified so that information (algorithm, data) inside is inaccessible to others; only the interface is visible. Reduces side effects of change
Functional independence modules with single-minded function and aversion to excessive interaction; measured by cohesion and coupling
Refinement top-down elaboration (Wirth's stepwise refinement): start with a high-level statement, detail it step by step. Abstraction and refinement are complementary
Aspects crosscutting concerns (logging, security) that affect many modules
Refactoring change that improves internal structure without changing the external behaviour
OO design concepts classes, objects, inheritance, encapsulation, polymorphism
Design classes refine analysis classes into software-realisable classes: user interface classes, business domain classes, process classes, persistent classes, system classes
Dependency inversion depend on abstractions, not on concretions (high-level modules shouldn't depend on low-level details)
Test-driven design design considers testability; write tests alongside
Cohesion and coupling
  • Cohesion = how strongly related the elements inside one module are (high is good). Spectrum (worst → best): coincidental → logical → temporal → procedural → communicational → sequential → functional
  • Coupling = degree of interdependence between modules (low is good). Spectrum (best → worst): data → stamp → control → external → common → content
  • Goal: high cohesion, low coupling
Coupling Description
Data modules share only simple parameters (best)
Stamp share a composite data structure (record) but use part
Control one module passes a flag controlling the other's logic
External share an externally imposed format, protocol, device
Common share global data
Content one module modifies the internal data / code of another (worst)
Modularity trade-off
Explanation

Abstraction means concentrating on what matters and hiding detail. A procedural abstraction is a named sequence of instructions, such as "open door", whose details are hidden. A data abstraction is a named collection of data, such as "door", with its attributes. Modularity divides software into separately named modules. Dividing into more modules reduces the effort to develop each module but increases the effort of integrating them, so there is an optimum number, shown at the lowest point of the total-cost curve.

Information hiding means a module's internal data and algorithm are invisible to others, who see only its interface, so a change inside the module does not spread. Functional independence is the result of modularity, abstraction and information hiding, and is measured with cohesion and coupling. Cohesion measures how closely the elements inside a module belong together, and the best kind is functional cohesion, where every element contributes to one task. Coupling measures how much modules depend on one another, and the best kind is data coupling, where only simple parameters are passed. The worst, content coupling, occurs when one module changes the inside of another. The aim is always high cohesion and low coupling.

Refinement is the process of elaborating a design from the top downwards, one level at a time, and complements abstraction. Refactoring is improving the structure of existing code without changing what it does. Separation of concerns says a complex problem is easier to solve if divided into independent concerns. An aspect is a concern, such as logging, that crosses many modules. Dependency inversion says that high-level modules should depend on abstractions, not on the details of low-level modules.
