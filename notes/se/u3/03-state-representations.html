Software Engineering · Unit III: Requirements Modeling and Design Concepts

State Representations
Subject
Software Engineering (24CS203)
Unit

Topic
3 of 9
Terms
State diagram, Sequence diagram, Use case

Practice: Part B questions for Unit III and Part A short questions.

On this page
  1. Two different characterisations of states
  2. Sequence diagram (behavior over time)
Notebook notes
Two different characterisations of states
  1. State of each class as the system performs its function
  2. State of the system as observed from the outside as the system performs its function
  • State of a class: passive state = current status of attributes (e.g. Player — position, orientation); active state = current status of the object as it undergoes a continuing transformation or processing
  • State transition: triggered by an event; may have a guard condition and action: event [guard] / action
  • State diagram (state chart) elements: initial pseudo-state (filled circle), states (rounded rectangle, with entry / do / exit actions), transitions (arrows), final state (circled dot)
  • Example: state diagram of a SafeHome control panel
Sequence diagram (behavior over time)
  • A sequence diagram shows how events cause flow from one object to another as a function of time; a short-hand version of a use case. Elements: lifelines (vertical dashed lines per object), messages (horizontal arrows; solid = call, dashed = return), activation bars, time runs downward
  • Built from the use case: identify objects → draw lifelines → add messages in order
  • Difference: state diagram = behaviour of one class/system across states; sequence diagram = interaction between several objects over time
Explanation

A behavioral model shows how the software reacts to events. It starts from the use cases. In each use case, find the points where information is exchanged between the actor and the system. Each such exchange is an event. For example, "homeowner enters a password" and "system displays an error" are both events. Each event is then connected to the objects that produce it and the objects that receive it.

A state diagram shows the states an object or the whole system can be in and the events that cause changes from one state to another. Think of a traffic signal or a vending machine. In the control-panel example, the system starts in a not-ready state, becomes ready when the sensors are ready, and then reads a password. A valid password leads to the selection of an operation, while an invalid one returns to reading. The notation for a transition is event [guard] / action, which means that when the event occurs and the guard condition is true, the action is performed and the state changes.

A sequence diagram looks at the same behaviour from a different angle. It shows the objects as vertical lifelines and the messages between them as horizontal arrows in time order from top to bottom. It is a compact version of a use case. The difference to remember is that a state diagram describes one object's life across many events, and a sequence diagram describes one scenario across many objects.
