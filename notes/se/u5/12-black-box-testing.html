Black-Box Testing

Software Engineering · Unit V: Software Testing

Black-Box Testing

Equivalence partitioning, Boundary value analysis, Debugging, Black-box testing

Practice: Part B questions for Unit V and Part A short questions.

On this page
  1. Example — equivalence partitioning and BVA
  2. Debugging (brief)
Notebook notes
  • Black-box (behavioral) testing focuses on the functional requirements of the software: enables the software engineer to derive sets of input conditions that fully exercise all functional requirements for a program. Complements white-box; uncovers different classes of errors
  • Errors found: incorrect or missing functions; interface errors; errors in data structures or external database access; behavior or performance errors; initialization and termination errors
  • Applied during later stages; questions answered: How is functional validity tested? How are system behavior and performance tested? What classes of input make good test cases? Is the system sensitive to certain input values? How are the boundaries of a data class isolated? What data rates and data volume can the system tolerate? What effect will specific combinations of data have on system operation?
  • Techniques
    1. Graph-based testing methods: understand the objects modeled in software and the relationships that connect them; create a graph — nodes = objects, links = relationships (directed link, bidirectional (symmetric) link, parallel links), node weights, link weights; then define tests to cover each node and link. Behavioral testing methods: transaction flow modeling, finite state modeling, data flow modeling, timing modeling
    2. Equivalence partitioning: divides the input domain into classes of data from which test cases can be derived. Each class is an equivalence class: if one value in the class finds an error, any would; if one doesn't, none would. Guidelines for defining classes
      • range → one valid and two invalid classes
      • specific value → one valid and two invalid
      • member of a set → one valid and one invalid
      • boolean → one valid and one invalid
    3. Boundary value analysis (BVA): a greater number of errors occurs at the boundaries of the input domain rather than in the "center". Select test cases at the edges of the class. Guidelines
      • range \(a..b\): test \(a\), \(b\), and just above and below (\(a-1\), \(a\), \(a+1\), \(b-1\), \(b\), \(b+1\))
      • number of values: min, max, just below min, just above max
      • apply to output conditions too; apply to internal data structures (array limits)
    4. Orthogonal array testing: for small input domains with many parameters where exhaustive testing is impractical: uses an orthogonal array to cover all pair-wise combinations (pairwise testing); detects and isolates all single-mode faults and many double-mode faults. E.g. 3 parameters × 3 values → 27 combos; L9 array → 9 tests
Example — equivalence partitioning and BVA
  • Requirement: a field accepts an integer age from 18 to 60
Class Range Test value Expected
Invalid (low) < 18 10 reject
Valid 18 – 60 35 accept
Invalid (high) > 60 75 reject
(also non-integer / empty) "abc" reject
  • BVA test values: 17 (reject), 18 (accept), 19 (accept), 59 (accept), 60 (accept), 61 (reject)
  • Number of tests: EP gives 3 (one per class); BVA gives 6 — use both
Debugging (brief)
  • Debugging process: test case → results → suspected causes → additional tests → identified cause → corrections → regression tests. Approaches: brute force, backtracking, cause elimination (binary partitioning), automated debugging (debugger, breakpoints, watches)
  • Psychological: debugging is frustrating — leads to bug-fixing mistakes; correct the cause, not the symptom. Fixing may introduce new bugs (regression)
  • Bugs: syntax, logic, runtime, interface, performance, security
Explanation

Black-box testing uses the specification to derive tests. Equivalence partitioning splits the inputs into classes whose members are expected to behave in the same way, so that one test from each class is enough. For a range of valid values there is one valid class and two invalid classes, one on each side. Boundary value analysis adds tests at and next to the edges of those classes, because errors cluster at boundaries, usually from mistakes such as using < where <= is needed. For a valid range from 18 to 60 the boundary tests are 17, 18, 19, 59, 60 and 61. Graph-based testing models objects and relationships as a graph and covers its nodes and links. Orthogonal array testing selects a small number of tests that cover all pairs of parameter values, which is helpful when the number of parameters is large and exhaustive testing is impossible.

Debugging begins after a test fails: the symptom is investigated, possible causes are suspected and tested, the cause is found and corrected, and regression tests are run to check that the correction has not introduced new errors. The rule is to correct the cause, not the symptom.
