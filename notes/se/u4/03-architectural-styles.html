Architectural Styles

Software Engineering · Unit IV: Software Design

Architectural Styles
Subject
Software Engineering (24CS203)
Unit
Unit IV: Software Design
Topic
3 of 12
Terms
Message passing, Kernel, Microkernel, Operating system

Practice: Part B questions for Unit IV and Part A short questions.

Notebook notes
  • Architectural style describes a system category that encompasses: (1) a set of components (database, computational modules) performing a function required by the system; (2) a set of connectors enabling communication, coordination and cooperation among components; (3) constraints defining how components can be integrated; (4) semantic models that enable a designer to understand overall properties of the system by analysing known properties of constituent parts
  • Taxonomy
Style Description Example
Data-centered a central data store (repository / blackboard) is accessed frequently by client software which adds, updates, deletes. Promotes integrability: clients are independent (added without affecting others) databases, IDEs, knowledge systems
Data-flow (pipe-and-filter) input data transformed by series of computational components (filters) connected by pipes; each filter is independent and works without knowledge of neighbours. Batch sequential variant: no incremental compilers, signal processing, Unix pipes
Call-and-return program structure that is easy to modify and scale: main program/subprogram architecture (function call hierarchy), remote procedure call (RPC) architecture (components distributed over networks) classic procedural programs, RPC
Object-oriented components encapsulate data and operations; communicate by message passing most OO systems
Layered layers: outermost = user interface, inner layers = utility, core; each layer provides services to the layer above and uses services from below. Layers hide complexity OS (kernel, drivers), network stack (OSI/TCP-IP), 3-tier web apps
  • Other styles: client–server, model–view–controller (MVC) (model = data, view = display, controller = handles input), microservices, event-driven, peer-to-peer, publish–subscribe, service-oriented (SOA), microkernel
  • Architectural patterns (vs style): address a specific behavioural issue within the context of an architectural style (e.g. concurrency, persistence, distribution)
  • Organisation and refinement: assess alternative architectural styles by control and data issues: control — how is it organised, hierarchical or distributed? data — how do components communicate, is data flow continuous or sporadic?
Explanation

An architectural style is a template for organising a system. It consists of components, the connectors that let them communicate, constraints on how they can be combined, and semantic models that help us predict the properties of the whole.

In the data-centred style, a central repository holds the data and independent clients read and write it. Clients can be added without affecting each other, which makes the system easy to integrate, but all clients depend on the repository's format. In the data-flow style, data passes through a series of independent filters connected by pipes, each knowing nothing about its neighbours. A compiler is a good example, with lexical analysis, parsing, and code generation as filters. The call-and-return style is the familiar structure of a main program calling subprograms, and in its remote procedure form the called components are on other machines. The object-oriented style combines data and operations in objects that communicate through messages. The layered style arranges the system in layers, in which each layer uses only the services of the layer below. The outer layer deals with the user interface and the inner layers with the system core. Operating systems and network protocol stacks are layered.

An architectural pattern is narrower than a style. It addresses a specific problem, such as how to deal with concurrency or persistence, within the context of a style.
