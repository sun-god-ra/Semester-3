Building the Requirements (Analysis) Model

Software Engineering · Unit II: Requirements Engineering

Building the Requirements (Analysis) Model
Subject
Software Engineering (24CS203)
Unit
Unit II: Requirements Engineering
Topic
5 of 13
Terms
Use case, Activity diagram, Class diagram, State diagram, Sequence diagram, Abstraction, Coupling

Practice: Part B questions for Unit II and Part A short questions.

Notebook notes
  • Analysis model = first technical representation of the system; uses text and diagrams. Its objectives: (1) describe what the customer requires, (2) establish a basis for design, (3) define a set of requirements that can be validated once the software is built
  • Elements of the analysis model
Element Contains Diagrams
Scenario-based how users interact use cases, activity diagrams, swimlane diagrams
Class-based objects, operations, relationships, collaborations class diagram, CRC models, collaboration diagrams, packages
Behavioral how the software responds to events state diagram, sequence diagram
Flow-oriented information flow and transformation data-flow diagrams (DFD), control-flow diagrams, processing narratives
  • Analysis rules of thumb: model should focus on requirements visible in the problem/business domain, high level of abstraction; each element adds to overall understanding; delay infrastructure and non-functional models to design; minimise coupling; model must provide value to all stakeholders; keep it as simple as possible
  • Domain analysis: identify, analyse and specify common requirements from a specific application domain for reuse (analysis patterns, frameworks)
  • Requirements modeling approaches: structured analysis (data and processes separate; DFD, ERD) vs object-oriented analysis (classes, attributes, operations)
Explanation

The analysis model is the first technical representation of what the system must do. It has three purposes: to describe what the customer needs, to give a starting point for design, and to define requirements that can be checked once the software is built. It is built from four kinds of elements. Scenario-based elements (use cases, activity diagrams) show how users interact. Class-based elements show the objects and their relationships. Behavioural elements show how the system reacts to events. Flow-oriented elements show how information moves and is transformed. A rule of thumb is that the analysis model should describe the problem and not the solution, so it is kept at a high level of abstraction and does not contain design details.
