Class-Based Modeling

Software Engineering · Unit II: Requirements Engineering

Class-Based Modeling

Terms

Practice: Part B questions for Unit II and Part A short questions.

On this page
  1. Identifying analysis classes
  2. Specifying attributes
  3. Defining operations
  4. CRC modeling
Notebook notes
  • Class-based modeling represents the objects the system manipulates, operations (methods) applied to the objects, relationships (some hierarchical) between the objects, and collaborations between the defined classes. Elements: classes and objects, attributes, operations, CRC models, collaboration diagrams, packages
Identifying analysis classes
  • Grammatical parse of the use-case narrative: nouns → candidate classes; verbs → operations
  • Potential classes come from the following types of things
    • External entities (other systems, devices, people) that produce or consume info
    • Things (reports, displays, letters, signals) part of the information domain
    • Occurrences / events (a property transfer, completion of a robot movement)
    • Roles (manager, engineer, salesperson) played by people
    • Organizational units (division, group, team)
    • Places (manufacturing floor, loading dock) that set the context
    • Structures (sensors, four-wheeled vehicles, computers) that define a class of objects
  • Selection characteristics for a class to be valid
    1. Retained information — needed to remember the info about it
    2. Needed services — operations that change attributes
    3. Multiple attributes — more than one (a class with a single attribute is better an attribute)
    4. Common attributes — applicable to all instances
    5. Common operations
    6. Essential requirements — external entities that produce/consume info are classes
  • Reject: class representing an implementation construct; a single attribute; something that is an operation; redundant (synonym)
Specifying attributes
  • Attributes = data items that describe the class (properties). Ask: "What data items fully define this class in the context of the problem?" e.g. class Player: name, position, defensive status, jersey number
  • Keep to what's needed for the problem; avoid design details
Defining operations
  • Operations = behaviour of the object (processing). Four categories: (1) manipulate data (add, delete, reformat, select); (2) perform computation; (3) inquire about the state of an object; (4) monitor for a controlling event
  • Parse the narrative for verbs; consider communication between objects (messages)
CRC modeling
  • CRC card (Class–Responsibility–Collaborator): index card with class name (top), responsibilities (left), collaborators (right). Developed by Beck & Cunningham
  • Responsibilities = attributes and operations relevant to the class ("something a class knows or does")
  • Collaborators = other classes required to provide information or help to complete a responsibility. Collaboration is a request from a client to a server
  • Types of classes (Wirfs-Brock)
    • Entity classes (model classes, business classes): extracted straight from the problem (e.g. FloorPlan, Sensor)
    • Boundary classes: create the interface (e.g. display, interactive screens, reports). Handle user interaction
    • Controller classes: manage unit of work — creation/update of entity objects, instantiate boundary objects, complex communication between objects, validation of data
  • Responsibilities guidelines
    1. Distribute system intelligence evenly (no god class)
    2. State each responsibility as generally as possible
    3. Put information and the behaviour that uses it in the same class
    4. Localise information about one thing in a single class
    5. Share responsibilities among related classes when appropriate
  • Collaborators: class collaborates if it sends / receives messages to fulfil a responsibility. Relationships: is-part-of, has-knowledge-of, depends-upon
Class: FloorPlan
Responsibility Collaborator
defines floor plan name / type
manages floor plan positioning
scales floor plan for display
incorporates walls, doors and windows Wall
shows position of video cameras Camera
Explanation

Class-based modeling finds the objects in the problem. A practical technique is the grammatical parse of the use case: the nouns are candidate classes and the verbs are candidate operations. A candidate is kept only if it passes selection tests, such as having information to remember, having multiple attributes, and having operations of its own. A noun with only one attribute is usually an attribute of another class, and a noun that is only an implementation detail is rejected.

Attributes are the data that describe the class, while operations are what it can do, in four groups: manipulating data, computing, inquiring about state, and watching for events. A CRC card records the class name, its responsibilities (what it knows or does), and its collaborators, the other classes it needs help from. Classes are grouped into entity classes (the real business concepts), boundary classes (the interface to users), and controller classes (which coordinate the work). The guidelines for assigning responsibilities say that intelligence should be spread evenly, so that no class does everything, and that data and the behaviour that uses it should be in the same class.
