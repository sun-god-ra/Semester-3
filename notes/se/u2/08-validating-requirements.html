Validating Requirements

Software Engineering · Unit II: Requirements Engineering

Validating Requirements
Subject
Software Engineering (24CS203)
Unit
Unit II: Requirements Engineering
Topic
8 of 13
Terms
Abstraction, Requirements engineering

Practice: Part B questions for Unit II and Part A short questions.

Notebook notes
  • Examine the specification to ensure that all requirements have been stated unambiguously, inconsistencies, omissions, errors detected and corrected; work products conform to standards
  • Requirements review (formal technical review) by the software engineers, customers, users and stakeholders. Questions:
    • Is each requirement consistent with the overall objective for the system/product?
    • Have all requirements been specified at the proper level of abstraction?
    • Is the requirement really necessary, or an add-on feature?
    • Is each requirement bounded and unambiguous?
    • Does each have an attribution (source)?
    • Do any requirements conflict with others?
    • Is each requirement achievable in the technical environment?
    • Is each requirement testable?
    • Does the requirements model properly reflect the information, function and behaviour of the system?
    • Has the model been partitioned so that information is progressively revealed?
    • Have requirements patterns been used?
  • Good requirements are correct, complete, consistent, unambiguous, verifiable, traceable, modifiable, ranked
Explanation

Negotiation in requirements engineering aims for a win–win outcome. The developers have to accept a set of requirements they can build within the constraints, and the customers must accept that not all wishes can be met at once. The steps are to identify the key stakeholders, to find the conditions each needs in order to feel they have won, and to reconcile these into a set all of them can accept.

Requirements keep changing, so they must be managed. A traceability table links each requirement to its source, its design element, code and tests. When a change request arrives, the table shows what else is affected, which allows an estimate of the impact on cost and schedule. A change control board decides whether to accept the change.

Validation is a review that asks whether the requirements are complete, consistent, unambiguous and testable. A requirement that cannot be tested cannot be shown to be met, so testability is one of the most important checks. Conflicts between requirements, requirements that cannot be achieved in the technical environment, and requirements that are only nice-to-have features should all be found at this stage, when they are cheap to fix.
