Developing Use Cases

Software Engineering · Unit II: Requirements Engineering

Developing Use Cases
Subject
Software Engineering (24CS203)
Unit
Unit II: Requirements Engineering
Topic
4 of 13
Terms
Use case

Practice: Part B questions for Unit II and Part A short questions.

Notebook notes
  • Use case = a text/graphical story of how an actor interacts with the system to achieve a goal, from the actor's viewpoint
  • Actor = anything that communicates with the system but is external (a person, device, another system). Primary actors interact directly to achieve a function; secondary actors support. An actor is a role, not a person
  • Steps to develop: identify actors → for each actor define goals → write the primary scenario (main flow) → alternative flows / exceptions
  • Writing a use case: name, primary actor, goal in context, preconditions, trigger, scenario (numbered steps), exceptions, priority, frequency, channel, secondary actors, open issues
  • Questions: What are the main tasks? What system information will the actor acquire/produce/change? Will the actor inform the system of changes? Does the actor wish to be informed of unexpected changes?
  • Example — SafeHome: "Access camera surveillance via the Internet — display camera views (ACS-DCV)"
    1. The homeowner logs onto the SafeHome Products website
    2. Enters user ID
    3. Enters two passwords
    4. System displays all major function buttons
    5. Homeowner selects "surveillance" from the major function buttons
    6. System displays thumbnail views of all cameras
    7. Homeowner selects a camera icon
    8. System displays the camera view in a window - Exception: ID or password incorrect → error message; invalid number of attempts → lock
  • Elements: actor (stick figure), use case (oval), system boundary (box), association (line), include (mandatory reuse: «include»), extend (optional / conditional extension: «extend»), generalisation
Explanation

A use case tells a story: an actor wants to achieve something with the system, and the use case lists the steps of the interaction from the actor's point of view. An actor is a role played by whoever or whatever interacts with the system from outside, so one person can play several actors and one actor can be played by several people. A good use case has a main scenario, a sequence of numbered steps for the normal case, and exceptions that describe what happens when things go wrong. In the use case diagram, ovals are use cases, stick figures are actors and the box is the system boundary. An include relationship says that one use case always uses another, as in the case of a login, while an extend relationship adds optional behaviour.
