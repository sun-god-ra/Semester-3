Term · OS Lab, Operating Systems

Internal fragmentation

  • Internal fragmentation — allocated memory may be slightly larger than requested; the size difference is memory internal to a partition but unused (e.g., hole of 18,464 bytes, request 18,462 → 2 bytes left; overhead to keep track of the tiny hole > the hole itself → allocate whole hole)

From Operating Systems › Contiguous Memory Allocation

  • Memory protection in paging: a protection bit with each frame (read-only / read-write / execute-only); a valid–invalid bit attached to each entry in the page table: "valid" = the associated page is in the process's logical address space, so a legal page; "invalid" = the page is not in the process's logical address space → trap. Or use PTLR. Some pages inside the page table range may be unused; internal fragmentation in addressing: because of the page granularity, process may reference addresses past its end up to the page boundary (still marked valid) — only the PTLR/valid bits catch pages beyond

From Operating Systems › Paging

  • Prepaging — bring in some or all of the pages a process will need before they are referenced (reduces the large number of page faults at process start-up; wasteful if pages are not used). Page size selection: fragmentation (small pages → less internal fragmentation), page-table size (large pages → small table), I/O overhead (seek and latency dominate → bigger is better), number of page faults, locality, TLB size and effectiveness (TLB reach = (TLB size) × (page size) — to increase: larger page size or multiple page sizes); typical 4 KB, trend toward larger. Program structure: e.g. a 128×128 array of ints, page size 128 words — row-major accessing for j { for i { data[i][j] = 0 } } → 128 × 128 = 16,384 page faults, while for i { for j { data[i][j] = 0 } } → 128 page faults — good data-structure and programming choices improve locality. I/O interlock and page locking: pages used for I/O must be pinned (locked) in memory so they are not replaced

From Operating Systems › Thrashing

  • Each file occupies a set of contiguous blocks on the disk. Directory entry has the starting block (address) and the length (number of blocks): file of n blocks starting at b occupies b, b+1, …, b+n−1. Advantages: simple (only the starting location and the length needed); supports both sequential and direct access — block i of a file that starts at b is at b + i (fast, minimal seek time: fewer seeks, head movement minimised). Disadvantages: finding space for a new file — first fit / best fit (dynamic storage-allocation problem) → external fragmentation (compaction is expensive: off-line (unmount) or on-line); determining how much space is needed for a file (file growth: find a larger hole and copy — slow; or overestimate → internal fragmentation; extent-based variant: contiguous chunk (extent) with additional contiguous chunk added when it runs out — file = one or more extents; the location of a file's blocks = address, block count, plus a link to the first block of the next extent; used in Veritas File System, ext4). Modified contiguous allocation scheme: when the allocated space is not large enough, another chunk (extent) is added

From Operating Systems › Allocation Methods

  • First fit: the first hole big enough; best fit: the smallest hole that is big enough (smallest leftover); worst fit: the largest hole (largest leftover). Leftover holes cause external fragmentation; unused space inside an allocated block is internal fragmentation
