Part B · Unit V

Software Testing

Software Engineering · 9 questions · Notes for this unit

Q1Nov 20258MCO5 K2

Explain the different levels of testing.

Answer
  1. Unit testing: tests each component or module in isolation (interface, local data, boundary conditions, independent paths, error handling). Done by the developer with drivers and stubs.
  2. Integration testing: tests the interfaces between modules as they are combined. Approaches: top-down, bottom-up, sandwich, big-bang; regression and smoke testing.
  3. System testing: tests the complete integrated system against the requirements: recovery, security, stress, performance, deployment tests.
  4. Acceptance testing: the customer confirms the system is acceptable (alpha at the developer's site, beta at the customer's site). Validation testing sits between integration and acceptance. Each level has a different aim: unit finds logic errors, integration finds interface errors, system finds requirement-level failures, acceptance builds confidence.
Q2Nov 20258MCO5 K2

Explain white-box testing techniques.

Answer

White-box (glass-box, structural) testing uses knowledge of the internal logic. Aims: exercise all independent paths, all logical decisions on true and false sides, all loops at their boundaries, and internal data structures.

Techniques:

  1. Basis path testing: flow graph → cyclomatic complexity → independent paths → test cases (see the example below).
  2. Control structure testing
    • Condition testing: exercise each logical condition.
    • Data-flow testing: select paths according to the definition and use of variables.
    • Loop testing: simple loops (skip, one pass, two passes, m passes, n−1, n, n+1), nested loops (innermost first), concatenated, unstructured (redesign).
  3. Statement, branch and path coverage. Benefits: finds hidden logic errors. Limits: needs the code, cannot find missing functions, costly for large programs.
Q3Nov 20258MCO5 K2

(OR) Explain the testing strategies for conventional software.

Answer

A strategy is a roadmap of what to test, how and in what order. Generic characteristics: conduct effective technical reviews first; testing begins at the component level and moves outward; different techniques at different times; testing is by the developer and an independent group; debugging is separate from testing.

The "spiral" of testing: unit → integration → validation → system testing (see levels above). Strategic issues: state the requirements in a quantifiable manner, specify the objectives, know the users, build robust software, use formal reviews and continuous improvement.

  • Unit test: driver and stub; checks interface, local data structures, boundary conditions, independent paths, error-handling paths.
  • Integration: top-down (stubs), bottom-up (drivers and clusters), regression, smoke (daily build).
  • Validation testing: success is when the software functions in a way the customer reasonably expects; includes configuration review and alpha/beta tests.
  • System testing: recovery, security, stress, performance and deployment testing.
Q4Nov 20258MCO5 K3

(OR) Explain basis path testing with an example.

Answer

Steps: (1) draw the flow graph from the code; (2) compute the cyclomatic complexity \(V(G)\); (3) list the independent paths; (4) design one test case for each path.

Program:

1  read(n); sum = 0; odd = 0;
2  while (n > 0) {
3     if (n % 2 == 0)
4         sum = sum + n;
5     else  odd = odd + 1;
6     n = n - 1;
   }
7  print(sum, odd);

Nodes N = 7, edges E = 8, predicate nodes P = 2 (nodes 2 and 3). \(V(G) = E - N + 2 = 8 - 7 + 2 = 3\); also \(P + 1 = 3\); regions = 3.

Independent paths:

  • Path 1: 1-2-7
  • Path 2: 1-2-3-4-6-2-7
  • Path 3: 1-2-3-5-6-2-7

Test cases:

Test Input n Path executed Expected (sum, odd)
T1 0 1-2-7 (0, 0)
T2 1 1-2-3-5-6-2-7 (path 3) (0, 1)
T3 2 1-2-3-4-6-2-3-5-6-2-7 (covers path 2 edges 3→4 and path 3) (2, 1)

Honest note: path 2 (1-2-3-4-6-2-7) on its own is infeasible for integer input. It needs a single even iteration after which \(n-1\le0\), but an even \(n>0\) gives \(n-1\ge1\). Infeasible paths are a known limit of basis path testing; the edge 3→4 is still covered by T3. In an exam, simply list the three independent paths and one input for each as above.

Q5Apr 20268MCO5 K2

Differentiate between internal and external views of testing.

Answer
  • Internal view = white-box testing: tester knows the code and tests the logic paths, loops and data structures. Done by developers.
  • External view = black-box testing: tester knows only the specification; tests the functions and the input/output behaviour without regard to the code. Done by testers or users.
White-box (internal) Black-box (external)
Based on the code structure Based on the requirements
Programming knowledge needed Not needed
Unit level mostly Higher levels (system, acceptance)
Finds logic errors Finds missing/incorrect functions, interface errors
Techniques: basis path, control structure Techniques: equivalence partitioning, BVA, graph-based, orthogonal arrays

They are complementary; "grey-box" testing mixes both.

Q6Apr 20268MCO5 K3

Explain the black-box testing strategies.

Answer

Black-box (behavioural) testing finds: incorrect or missing functions, interface errors, data-structure or external-database errors, behaviour/performance errors, and initialisation/termination errors.

  1. Graph-based testing: build a graph of objects (nodes) and relationships (links); design tests that cover each relationship.
  2. Equivalence partitioning: divide the input domain into classes of valid and invalid data; one test case per class. Example: age 18 to 60 → classes: <18 (invalid), 18–60 (valid), >60 (invalid).
  3. Boundary value analysis (BVA): test at the edges of classes: for 18–60 test 17, 18, 19, 59, 60, 61.
  4. Orthogonal array testing: for inputs with few values but many combinations, pick a small balanced set of combinations.
  5. Other: comparison testing, cause–effect graphing, error guessing.
Q7Apr 20268MCO5 K2

(OR) Explain integration testing.

Answer

Integration testing builds the program structure while testing for interface errors. Avoid "big bang"; use an incremental approach.

  • Top-down: start with the main control module, add subordinate modules depth-first or breadth-first; stubs replace missing lower modules. Early check of main control; needs many stubs.
  • Bottom-up: start from atomic (lowest-level) modules, grouped into clusters (builds) tested with drivers; no stubs needed; the top is checked late.
  • Sandwich (hybrid): top-down on the upper layers plus bottom-up on the lower.
  • Regression testing: re-execute a subset of tests after each change/addition.
  • Smoke testing: daily build of the integrated product tested by a fixed set of tests (used in time-critical projects).
Q8Apr 20268MCO5 K2

(OR) Differentiate between alpha and beta testing.

Answer
Point Alpha testing Beta testing
Where At the developer's site At the customer's / end-user's site
Who A representative group of end users with the developer observing Real end users, developer not present
Environment Controlled Uncontrolled, live
Recording Developer records errors and usage problems Customer records problems and reports them periodically
Stage Before beta After alpha, just before release
Fixes Easy to fix issues quickly Feedback used for the final release

Both are acceptance tests, used when the software has many end users and a formal acceptance test per customer is impractical.

Q9Expected8MCO5 K2

Differentiate between verification and validation. Explain software quality assurance.

Answer

Verification: are we building the product right? – reviews, walkthroughs, inspections, static analysis. Validation: are we building the right product? – dynamic testing and acceptance.

Software quality assurance (SQA) is an umbrella activity that applies to every process step: standards and procedures, formal technical reviews, a multi-tiered testing strategy, control of documentation and changes, enforcement of standards, and measurement and reporting. Goal: build quality in rather than test it in.
