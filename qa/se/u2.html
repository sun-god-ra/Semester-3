Part B · Unit II

Requirements Engineering

Software Engineering · 8 questions · Notes for this unit

Q1Nov 20258MCO2 K2

Explain the requirements models in software engineering.

Answer

Requirements modelling (analysis modelling) represents the requirements in a form that is easy to understand and check. Elements:

  1. Scenario-based models: use cases, activity diagrams, swimlane diagrams. User's viewpoint.
  2. Class-based models: analysis classes, attributes, operations, CRC cards, class diagrams. Static structure.
  3. Behavioural models: state diagrams, sequence diagrams. How the system responds to events.
  4. Flow-oriented models: data flow diagrams, control flow diagrams, data dictionary. How data is transformed.
  5. Data models: entity–relationship diagrams for data objects.

Goals: describe what the customer requires, establish a basis for design, and define a set of requirements that can be validated.

Q2Nov 20258MCO2 K3

Explain class-based modelling and CRC modelling with an example.

Answer

Class-based modelling identifies the classes the system manipulates, their attributes (data) and operations (behaviour), and the relationships between them.

Steps: (1) identify classes by taking the nouns from the use case narrative; (2) classify them as external entities, things, events, roles, organisational units, places, structures; (3) select those satisfying: retained information, needed services, multiple attributes, common attributes and operations, essential requirements; (4) define attributes and operations; (5) draw the class diagram.

CRC modelling. A CRC card has: class name; responsibilities (what the class does or knows); collaborators (other classes needed to fulfil a responsibility). Class types: entity, boundary and controller.

Example, library system:

Class: Book
Responsibilities Collaborators
knows title, ISBN, status
mark as issued / returned Loan
Class: Loan
Responsibilities Collaborators
records member, book, due date Member, Book
compute fine Fine
Q3Nov 20258MCO2 K2

(OR) Explain the requirements engineering tasks.

Answer

Requirements engineering (RE) builds a bridge between the needs and the design. Seven tasks:

  1. Inception: understand the basic problem, who wants the solution, the nature of the solution; establish a first communication with the stakeholders.
  2. Elicitation: collect requirements by interviews, questionnaires, observation, Joint Application Development, collaborative meetings, QFD. Problems: scope, understanding, volatility.
  3. Elaboration: expand and refine into a technical model (scenarios, classes, data), user scenarios and attributes.
  4. Negotiation: reconcile conflicts between stakeholders, rank requirements by priority, adjust cost and risk (win-win).
  5. Specification: produce the SRS document (written document, models, prototype, scenarios).
  6. Validation: formal technical reviews check for errors, omissions, ambiguity, conflict, testability.
  7. Requirements management: identify, trace and control changes through traceability tables.
Q4Nov 20258MCO2 K3

(OR) Explain use case modelling with an example.

Answer

A use case describes a sequence of actions by an actor and the system's responses that yields an observable result of value.

Building a use case: identify the actors (primary and secondary), then for each actor write the goals (use cases), then the narrative: preconditions, main (basic) flow, alternate flows, exceptions, postconditions.

Example: Use case: Withdraw cash (ATM)

  • Primary actor: Customer. Secondary actor: Bank server.
  • Precondition: the card is valid and the customer has been authenticated.
  • Main flow: (1) customer selects Withdraw; (2) system asks for the amount; (3) customer enters the amount; (4) system verifies the balance with the bank; (5) system dispenses cash and updates the balance; (6) system prints the receipt and returns the card.
  • Alternate flow: amount exceeds the balance → the system shows an error and asks for a lower amount.
  • Exception: the machine has no cash → the system cancels the transaction.
  • Postcondition: the account is debited and the transaction is logged.
Q5Apr 20268MCO2 K2

Explain the problems encountered in requirements engineering (elicitation).

Answer

Christel and Kang identified:

  • Problems of scope: the boundary of the system is ill-defined, or unnecessary technical detail is given.
  • Problems of understanding: customers don't know what they want, don't understand their own computing environment, don't have a full understanding of the domain, omit "obvious" information, specify requirements that conflict with others, or specify unclear and untestable requirements.
  • Problems of volatility: requirements change over time.

Additional: stakeholders in conflict, communication gaps with developers, missing implicit requirements, politics, inadequate access to users. Remedy: prototypes, collaborative meetings, scenarios, early reviews and a change-control process.

Q6Apr 20268MCO2 K2

Explain requirements negotiation.

Answer

The aim is a set of requirements that satisfies the stakeholders and is achievable. Stakeholders often ask for more than the budget and time permit and may conflict with each other. Negotiation activities:

  1. Identify the key stakeholders (those who will take part).
  2. Determine each stakeholder's "win conditions".
  3. Negotiate: work out a set of requirements that all parties agree on (win–win).

Practice: rank requirements by priority (must/should/could), estimate their cost and risk, drop or defer some, and record the agreement. The aim is that nobody ends up a "loser", or the loser later undermines the project.

Q7Apr 20268MCO2 K3

(OR) Explain scenario-based modelling.

Answer

Scenario-based modelling is the first part of requirements modelling. Since the user's view is easiest to understand, we start with how the actors use the system.

  • Writing use cases: actors, goals, main flow, alternatives, exceptions (see the use-case answer above).
  • Activity diagrams: a flowchart of the flow of control in a use case, with decisions, forks and joins.
  • Swimlane diagrams: an activity diagram divided into lanes, one for each actor or class, showing who does which activity.
  • Use case diagrams: overview of actors and use cases.
Q8Apr 20268MCO2 K2

(OR) Explain requirements validation.

Answer

Validation checks that the requirements model is correct and acceptable before design starts. Main tool: the formal technical review by developers, customers and users. Questions to ask:

  • Is each requirement consistent with the overall objective?
  • Are all specified at the right level of abstraction? Is it unambiguous?
  • Is the requirement necessary, or an add-on feature?
  • Is each testable, and achievable in the technical environment and budget?
  • Has the source been identified; does it conflict with others?
  • Does it have traceability to the system and project objectives?
  • Is it complete (nothing missing), and does the model reflect the information, function and behaviour? Other: prototype evaluation, test-case generation from requirements, and checklists. Errors found here are cheapest to fix.
