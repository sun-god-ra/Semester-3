Part B · Unit III

Requirements Modeling and Design Concepts

Software Engineering · 7 questions · Notes for this unit

Q1Nov 20258MCO3 K2

Explain the role of abstraction in design.

Answer

Abstraction lets us concentrate on the essential features and ignore low-level detail; at each level of the design we use a higher level of abstraction and refine downwards (stepwise refinement).

  • Procedural abstraction: a named sequence of instructions with a specific, limited function, e.g. open a door (walk to door, reach, grasp knob, turn, pull). We use the name and not the steps.
  • Data abstraction: a named collection of data describing a data object, e.g. door with attributes type, swing direction, weight, dimension. Procedural abstraction open then uses the data abstraction door.
  • Control abstraction: e.g. synchronisation semaphore.

Benefits: manage complexity, hide detail (information hiding), allow changes in implementation, support reuse and parallel development. Related: refinement is the process of elaboration (abstraction and refinement are complementary).

Q2Nov 20258MCO3 K3

Explain requirements modelling for mobile apps.

Answer

Mobile apps (MobileApps) have special constraints, so the requirement model must reflect them:

  • Context: small screen, touch input, intermittent connectivity, limited battery, memory and processing, sensors (GPS, camera, accelerometer), many device models and OS versions.
  • Scenario-based: user stories and use cases for short, task-oriented sessions; include interruptions (calls, notifications, loss of network), and offline mode.
  • Class-based: classes for the user, session, data cache, device sensors, permissions, sync service.
  • Behavioural: state diagram for lifecycle (foreground, background, suspended, terminated) and for connectivity states.
  • Non-functional: responsiveness, battery use, security (permissions, storage), accessibility, usability for touch, app-store rules.
  • Navigation/Interface: screen flow (storyboard) and navigation model.
  • Data/sync: local storage and server synchronisation.
Q3Nov 20258MCO3 K2

(OR) Explain the design concepts that improve software quality.

Answer

Fundamental concepts (Pressman):

  1. Abstraction: procedural and data abstraction.
  2. Architecture: the overall structure; chosen style (layered, MVC...).
  3. Patterns: reusable solutions to known problems.
  4. Separation of concerns: break a problem into parts that can be solved independently.
  5. Modularity: divide the software into separately named, addressable components (modules); improves manageability.
  6. Information hiding: modules hide internal data and procedures; only the interface is visible.
  7. Functional independence: single-minded modules with low interaction; measured by high cohesion and low coupling.
  8. Refinement: stepwise elaboration from high-level statement to detail.
  9. Aspects: crosscutting concerns (security, logging).
  10. Refactoring: improve internal structure without changing behaviour.
  11. Object-oriented design concepts: classes, inheritance, polymorphism, encapsulation.
  12. Design classes, and dependency inversion.

Quality impact: high cohesion and low coupling → easy to test, modify and reuse; information hiding → fewer ripple effects.

Q4Nov 20258MCO3 K2

(OR) Explain object-oriented design concepts.

Answer
  • Class: template of attributes and operations. Object: instance of a class.
  • Encapsulation: data and operations are packed together; internal details are hidden behind the interface.
  • Inheritance: a subclass acquires the attributes and operations of its superclass, enabling reuse and specialisation (generalisation/specialisation).
  • Polymorphism: the same message (operation) behaves differently on different objects; overloading and overriding.
  • Abstraction: abstract classes and interfaces.
  • Messages: objects communicate by sending messages; coupling is through messages.
  • Design classes: user-interface classes, business-domain classes, process classes, persistent classes, system classes. Good design classes are complete and sufficient, primitive, have high cohesion and low coupling.
  • Class diagram shows association, aggregation, composition, generalisation and dependency.
Q5Apr 20268MCO3 K3

Explain requirements modelling for web applications: the interaction and configuration models.

Answer

Requirements model for WebApps has content, interaction, functional, navigation and configuration models.

  • Interaction model: how the user interacts with the page. Components: use cases, sequence diagrams (user ↔ browser ↔ server), state diagrams (page states, e.g. logged-out, logged-in), and the user interface prototype (layout, navigation, forms).
  • Configuration model: describes the environment in which the WebApp lives – server-side (web server, application server, database, OS, middleware, firewalls, security) and client-side (browsers, versions, screen sizes, plug-ins, mobile). Shown by deployment diagrams and a textual list of constraints, and it is concerned with scalability and security.
Q6Apr 20268MCO3 K2

(OR) Explain object-based modelling (class-based modelling).

Answer

Object-based (class-based) modelling represents the objects the system will manipulate, the operations applied to them, the relationships between them and the collaborations. Steps and elements: identify classes (noun analysis from use cases), attributes, operations (verbs), CRC cards, class diagram, class packages, and behavioural modelling by state diagram and sequence diagram. See the CRC answer in Unit II for the worked example.

Q7Apr 20268MCO3 K2

(OR) Explain component-level design elements and deployment-level design elements.

Answer

Component-level design elements describe the internals of each software component: its interface, the data structures, the algorithms (in pseudocode or flowchart), the control logic and the processing. Shown as UML component diagrams, class diagrams with operations, activity diagrams and state diagrams. They lead directly to code.

Deployment-level design elements show how software functionality and subsystems are allocated to the physical computing environment (nodes, servers, devices, networks). Shown as UML deployment diagrams: nodes (e.g. PC, application server, database server) connected by communication links, each with the artifacts (software) deployed on it.
