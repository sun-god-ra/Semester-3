Software Design

Software Engineering · 8 questions · Notes for this unit

Q1Nov 20258MCO4 K2

Explain the design decisions in architectural design.

Answer

Architectural design decisions are the choices that shape the structure and decide whether quality attributes are met. A sound architecture answers:

  1. Is there a generic application architecture to reuse (web, transaction processing, language processing)?
  2. How will the system be distributed (client–server, multi-tier, cloud) across hardware?
  3. Which architectural patterns/styles fit (layered, MVC, pipes and filters, repository, microservices)?
  4. How to decompose into subsystems and modules, and how they communicate (shared data, messages, calls)?
  5. How to meet the non-functional requirements: performance (localise critical operations), security (layered with protection), safety, availability (redundancy), maintainability (small replaceable parts).
  6. Control strategy: centralised or event-driven.
  7. How to document the architecture (views). Each decision involves trade-offs (e.g. security vs performance); record the rationale.
Q2Nov 20258MCO4 K2

Explain the web application design concepts.

Answer

WebApp design covers six areas:

  • Interface design: layout, navigation, aesthetics, consistent look.
  • Aesthetic design: colour, fonts, graphics, images.
  • Content design: structure and presentation of text, graphics, audio and video.
  • Architecture design: overall content structure (linear, grid, hierarchical, networked/web) and the functional architecture (e.g. MVC, multi-tier).
  • Navigation design: how users move through the content; semantics of navigation units, syntax of navigation (links, menus, tabs, breadcrumbs).
  • Component-level design: functional components (forms, search, shopping cart). Principles: simplicity, consistency, identity, robustness, navigability, visual appeal, compatibility; follow the MVC pattern to separate model, view and controller.
Q3Nov 20258MCO4 K2

(OR) Explain the architectural styles.

Answer

An architectural style defines a set of component types, connectors, constraints on how to combine them and a semantic model.

  1. Data-centred: a central data store (repository/blackboard) accessed by independent clients; easy to integrate, the store is a bottleneck.
  2. Data-flow (pipe and filter): filters transform data and pass it through pipes; good for batch processing and compilers.
  3. Call and return: main program/subprogram, remote procedure call, and layered architecture (each layer serves the one above).
  4. Object-oriented: components are objects that encapsulate data and operations; communicate by messages.
  5. Layered: presentation, application, data, each layer with a defined responsibility.

Choose by the quality attributes needed; most real systems combine several.

Q4Nov 20258MCO4 K3

(OR) Explain the interface analysis and design steps.

Answer

Interface analysis studies the people who will use the interface (user analysis), the tasks they perform (task analysis), the content to display, and the environment (hardware, lighting, mobility). User analysis asks: who are the users, their skills, their goals, how they work.

Interface design steps

  1. Use the analysis to define interface objects and actions (operations).
  2. Define events (user actions) that change the state of the interface.
  3. Depict each interface state as the user sees it.
  4. Indicate how the user interprets the state from the information shown. Also: design the layout, menus, icons, messages and help; build a prototype; evaluate for usability. The design issues: response time, help facilities, error handling, menu and command labelling, application accessibility, internationalisation.
Q5Apr 20268MCO4 K2

Explain the golden rules of user interface design.

Answer

Theo Mandel's three golden rules:

  1. Place the user in control
    • Define modes of interaction so that the user is not forced into unnecessary actions.
    • Provide flexible interaction (keyboard, mouse, voice).
    • Allow interaction to be interruptible and undoable.
    • Streamline interaction as skill levels advance; allow customisation.
    • Hide technical internals from the casual user.
    • Design for direct interaction with the objects on the screen.
  2. Reduce the user's memory load
    • Reduce demand on short-term memory.
    • Establish meaningful defaults.
    • Define shortcuts that are intuitive.
    • The visual layout should be based on a real-world metaphor.
    • Disclose information progressively.
  3. Make the interface consistent
    • Allow the user to put the current task into a meaningful context.
    • Maintain consistency across a family of applications.
    • If past interactive models have created user expectations, do not change them without a good reason.
Q6Apr 20268MCO4 K3

Explain architectural decisions with an example.

Answer

Example: Online shopping system.

  • Decision 1, distribution: multi-tier client–server, so that the web client, application server and database server can scale separately.
  • Decision 2, style: layered MVC (presentation → business logic → data access) for modifiability.
  • Decision 3, performance: cache product catalogue; put the checkout and payment on dedicated servers.
  • Decision 4, security: put payment in the innermost layer behind a firewall, with encryption (TLS) and authentication.
  • Decision 5, availability: replicate the database and use a load balancer.
  • Decision 6, integration: use a REST interface to a third-party payment gateway.

Trade-off recorded: caching improves speed but needs invalidation.

Q7Apr 20268MCO4 K2

(OR) Explain software architecture and quality attributes.

Answer

Software architecture is the structure of the system: components, their externally visible properties and their relationships. Bass, Clements and Kazman: architecture is a vehicle for stakeholder communication, an early design decision set and a transferable abstraction.

Quality attributes the architecture must support:

  • Runtime: performance, security, availability, reliability, usability, safety.
  • Development-time: modifiability, testability, portability, reusability, interoperability.

How the architecture supports them: performance by localising operations and reducing communication; security by layering with critical assets in the inner layer; availability by redundancy; modifiability by small, self-contained, loosely coupled components; testability by well-defined interfaces. There are trade-offs between attributes (e.g. security vs usability), which are analysed with scenarios (ATAM).

Q8Apr 20268MCO4 K2

(OR) Explain component-level design techniques.

Answer

Component-level design (completed after the architecture) refines the architectural components to a level that is nearly code.

  • Definition: a component is a modular, deployable, replaceable part of a system that encapsulates implementation and exposes a set of interfaces.
  • Views: object-oriented (classes, with the analysis class elaborated into a design class with all attributes, operations and interfaces) and traditional (a processing element with its data structures and the algorithm).
  • Design principles: Open–Closed, Liskov Substitution, Dependency Inversion, Interface Segregation, Release Reuse Equivalency, Common Closure, Common Reuse.
  • Guidelines: naming conventions, interfaces, dependencies and inheritance.
  • Cohesion types (aim for functional): utility, layer, communicational, sequential, procedural, temporal.
  • Coupling types (aim for low): content, common, control, stamp, data, routine call, type use, inclusion/import, external.
  • Conducting the design: identify the classes from the problem domain and the infrastructure; elaborate; describe persistent data sources; develop behavioural representations; elaborate deployment diagrams; refactor.
  • Notation: UML, pseudocode, flowcharts, decision tables, and the structured-programming constructs (sequence, condition, repetition).
