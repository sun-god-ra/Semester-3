Part B · Unit III

Process Synchronization and Deadlocks

Operating Systems · 6 questions · Notes for this unit

Q1Nov 20258MCO3 K2

Explain monitors.

Answer

A monitor is a high-level synchronisation construct: an abstract data type whose shared data can be accessed only through the monitor's procedures, and only one process can be active in the monitor at a time.

monitor Buffer {
    int count = 0;                 // shared data
    condition notFull, notEmpty;   // condition variables
    procedure insert(item) {
        if (count == N) notFull.wait();
        add item; count++;
        notEmpty.signal();
    }
    procedure remove() {
        if (count == 0) notEmpty.wait();
        take item; count--;
        notFull.signal();
    }
}
  • Condition variables x: x.wait() suspends the calling process until another process calls x.signal(), which resumes exactly one suspended process (no effect if none waits, unlike a semaphore).
  • With signal, the signaller and the resumed process must not both be active: signal and wait (signaller waits) or signal and continue (resumed waits).
  • Java's synchronized with wait()/notify() implements the idea.
Q2Nov 20258MCO3 K2

Explain semaphores.

Answer

A semaphore \(S\) is an integer variable accessed only through two atomic operations:

wait(S)   { while (S <= 0) ;  S--; }     // P
signal(S) { S++; }                       // V
  • Binary semaphore (0/1, like a mutex lock) and counting semaphore (number of resource instances).
  • Busy waiting (spinlock) wastes CPU; the blocking implementation puts the process in a waiting queue and wakes it up on signal, so S can become negative (its magnitude = waiting processes).
  • Mutual exclusion: wait(mutex); critical section; signal(mutex); with mutex = 1.
  • Ordering: to run S2 after S1, use a semaphore initialised to 0.
  • Problems: wrong order or a missing signal causes deadlock or violates mutual exclusion; also priority inversion. Classic uses: bounded buffer (mutex=1, empty=n, full=0), readers–writers, dining philosophers.

Q4Nov 20258MCO3 K2

(OR) Explain deadlock prevention.

Answer

Deadlock: a set of processes each waiting for a resource held by another in the set. It needs four conditions together (mutual exclusion, hold and wait, no pre-emption, circular wait). Prevention ensures that at least one of them can never hold:

  1. Mutual exclusion: make resources sharable (read-only files). Not possible for inherently non-sharable resources (printer).
  2. Hold and wait: a process must request all its resources at once before it starts, or may request only when it holds none. Drawbacks: low resource use, starvation.
  3. No pre-emption: if a process holding resources requests another that is unavailable, it releases all that it holds (they are pre-empted), or a resource is taken from a waiting holder. Works for CPU registers and memory, not for printers.
  4. Circular wait: impose a total ordering of resource types, \(F: R\to N\), and make processes request resources in increasing order only. This is the most practical method. Side effect of prevention: poor device utilisation and reduced throughput.
Q5Expected8MCO3 K3

Explain the Banker's algorithm with an example.

Answer

Deadlock avoidance: each process declares its maximum need; a request is granted only if the system stays in a safe state (a safe sequence exists). Data structures (n processes, m resource types): Available[m], Max[n][m], Allocation[n][m], Need = Max − Allocation.

Safety algorithm: Work = Available; Finish[i] = false. Find i with Finish[i] = false and Need[i] ≤ Work; set Work += Allocation[i], Finish[i] = true; repeat. If all finish → safe.

Example (A, B, C): Available = (3, 3, 2)

Allocation Max Need
P0 0 1 0 7 5 3 7 4 3
P1 2 0 0 3 2 2 1 2 2
P2 3 0 2 9 0 2 6 0 0
P3 2 1 1 2 2 2 0 1 1
P4 0 0 2 4 3 3 4 3 1

Work = (3,3,2). P1 (1,2,2 ≤ work) → Work = (5,3,2). P3 → (7,4,3). P4 → (7,4,5). P0 → (7,5,5). P2 → (10,5,7). Safe sequence ⟨P1, P3, P4, P0, P2⟩: the state is safe.

Q6Expected8MCO3 K3

Explain the classical problems of synchronization (bounded buffer, readers–writers, dining philosophers).

Answer

Bounded buffer: semaphores mutex = 1, empty = n, full = 0.

Producer: wait(empty); wait(mutex); add item; signal(mutex); signal(full);
Consumer: wait(full);  wait(mutex); remove item; signal(mutex); signal(empty);

Readers–writers: many readers may read together, a writer needs exclusive access. rw_mutex = 1, mutex = 1, read_count = 0. First reader locks rw_mutex, last reader releases it. Writer: wait(rw_mutex); write; signal(rw_mutex);. This first version can starve writers.

Dining philosophers: 5 philosophers, 5 chopsticks (semaphore each). Naive solution: each picks left then right; if all pick the left, deadlock. Remedies: at most 4 philosophers sit, pick both chopsticks only if both are available (inside a critical section), or asymmetric pick (odd: left first, even: right first).
